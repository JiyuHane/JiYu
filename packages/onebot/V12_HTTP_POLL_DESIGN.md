# OneBot v12 HTTP event polling: future design

## Status and reference

This is a design note, not a feature announcement. `get_latest_events` is not implemented by the current v12 dispatcher. The HTTP transport has an optional internal poll-capability seam, but production does not inject it. An internal runtime seam can explicitly activate an in-memory poll owner, but production code does not currently activate or expose it. Neither seam provides production HTTP polling. In particular, this document does not claim complete OneBot v12 support.

The [OneBot 12 candidate meta-action specification](https://12.onebot.dev/interface/meta/actions/) requires `get_latest_events` for HTTP: return non-meta events from oldest to newest; `limit` defaults to 0, meaning no count limit; `timeout` defaults to 0, meaning no wait, and is expressed in seconds. A bounded implementation must disclose its queue and response constraints; a bounded buffer is not an unbounded interpretation of `limit: 0`. Overflow and shutdown loss must be observable.

## Current code, not the proposed behavior

- [Runtime](src/v12-runtime/runtime.ts) constructs `self` from the account context and creates a per-account `V12Dispatcher`. Its binding signature includes host, port and access token. It converts supported v11 events and publishes them to subscribers. An explicitly activated internal [poll owner](src/v12-runtime/poll-owner.ts) can additionally enqueue events with a valid source ticket; no current production caller activates that owner, so this does not provide HTTP polling.
- [Dispatcher](src/v12/dispatcher.ts) snapshots JSON-shaped requests before processing. Its constructor copies `options.self` and version; an explicitly supplied `self` must be valid and match both platform and user ID. The supported-action list does not contain `get_latest_events`. The candidate [action response specification](https://12.onebot.dev/connect/data-protocol/action-response/) says a nonempty request `echo` should be returned unchanged: this is a SHOULD, not a MUST, and it does not require echoing an empty string. Jiyu preserves a supplied string `echo`, including `""`, on normal action success and failure when it can be safely observed; an absent echo is omitted. Request snapshots have explicit shape and size limits; see [validation](src/v12/validation.ts). The transport's early HTTP failures occur before an action body has been parsed and thus do not have a request echo to preserve.
- The dispatcher's internal HTTP preflight can classify poll parameters, but is not connected to the transport and does not run a poll. For an ordinary action it freezes an opaque token and stores the private request snapshot in a WeakMap; the request snapshot itself is isolated from the original input but is not frozen. A token is consumed at most once by that dispatcher; it is not by itself a same-process security capability or an automatic epoch revocation mechanism. Any future owner must define creation, bounded lifetime and release or invalidation separately.
- [Transport](src/v12-network/index.ts) serves HTTP and WebSocket. For an HTTP action it checks open/quiesced state, path, authentication, method, content type, response admission, request body size and UTF-8/JSON parsing. When the configured access token is nonempty, an Authorization header takes precedence over the query token; with an empty token the auth helper accepts without checking either. Defaults include 1 MiB request body, 1 MiB output, 128 connections and 15 seconds; constructor options can override them. The default 64 limit is applied separately to the HTTP `responses` set and to `active` handler dispatches shared by HTTP and WebSocket, not to their sum. These are transport defaults, not poll-buffer defaults.
- When a trusted host explicitly supplies the optional HTTP poll capability, the transport can route an admitted `get_latest_events` request to it using a guarded sink. The host remains responsible for shared preflight, readiness and ordering checks, tracking the original task, and completing all writes before its promise settles; arbitrary same-process writers are outside that contract. The default runtime supplies no capability. Fake response tests do not establish socket behavior or remote receipt.
- After the HTTP body is parsed once with `JSON.parse`, duplicate object member names have JavaScript's last-value-wins semantics. Future preflight and response echo handling must use that same parsed request, not reparse or derive different echo values. In the current transport, `requestEcho(input)` precedes the `validRequest` shape check, the `active` busy check, handler invocation (where dispatcher preflight currently runs), and response normalization. The separate HTTP `responses.size` busy check happens before reading the body, so that response has no parsed request echo. Moving detailed classification ahead of the busy check would change existing error precedence; preserve this order when integrating the HTTP preflight.
- The HTTP body-read timer is cleared after parsing; ordinary `dispatch` separately races the actual handler against its timeout. The optional poll path instead aborts and destroys its response at its deadline while continuing to observe the original task; it cannot forcibly settle a trusted host promise. Both use the configured timeout, but these are separate 15-second timers by default, not one end-to-end deadline. A standalone server also sets `headersTimeout` and `requestTimeout`; in attach mode the host owns socket and header/idle deadlines. An `active` slot is held until the underlying handler settles even when the race times out. For an ordinary action, closing a response sets the outer request as settled and cleans its bookkeeping but does not cancel the underlying action. For an injected poll capability, close or quiesce signals cancellation; an unsettled host promise can continue to occupy its active slot. `quiesce` destroys active HTTP responses and WebSocket clients.
- A v12 action response uses `status`, `retcode`, `data`, `message` and optional string `echo`. `dispatch` validates the handler response and normalizes failed responses before `json` calls `encodeResponse`; many failure messages are replaced by a fixed outcome-unknown message, while retcode and request echo are preserved. `encodeResponse` serializes the normalized object once, checks the resulting UTF-8 size and `data`, then attempts a fixed failure fallback retaining echo if needed. If the fallback exceeds the cap, ordinary action responses close the connection. HTTP errors before parsing use the same envelope when it fits, but 401/415 may instead send an empty body if the cap is too small; upgrades and destroyed connections are not universal JSON envelopes. See the [transport tests](tests/v12-network/transport.test.ts), including empty echo and serialization cases.
- The [poll buffer](src/v12-runtime/event-poll-buffer.ts) is a synchronous-enqueue/async-reserve, bounded FIFO used by the explicitly activated internal poll owner. Its `PollResult` is a mutable ordinary object; the returned token is checked by that buffer's `commit` and `release`, but there is no authenticated owner identity or special trusted result tag. After reservation, abort does not release the token; there is no active-reservation lease timer. An abandoned reservation blocks later polls. `close()` revokes the token and discards queued data; held `eventsJson` strings remain usable. Queue, batch and event limits count encoded array bytes, not the full HTTP envelope or actual process RSS. The buffer requires the owner to validate event schema, account and source epoch. Its [offline tests](tests/v12-runtime/event-poll-buffer.test.ts) describe the current prototype, not a running HTTP service.
- The [poll transaction](src/v12-runtime/poll-transaction.ts), used by the explicitly activated internal owner but not by production HTTP, retains the bounded empty-array success for queue `empty` or `timeout` under its legacy policy. Under the ordered policy these states instead return an internal `empty_unresolved` outcome without writing a success. A timeout says only that this poll did not obtain a batch: another reservation may still hold events. Its local `finish` is not a remote acknowledgement. These are component semantics under its trusted owner and queue contracts; transport integration and consumer-group policy remain to be reviewed.

## Ownership and epochs for a future integration

One explicitly owned buffer/consumer group should be bound to one account and one authorization/binding epoch. A transport-owned coordinator should hold each selected token until it commits or releases it; clients and general action handlers must not receive the token or supply raw `eventsJson`. Obtaining a reservation only through that coordinator establishes its intended provenance; this is not proof that arbitrary same-process objects, modified built-ins, or hostile code are safe. The current buffer itself does not authenticate its owner. Account identity and source epoch must be validated before enqueue, since the buffer validates neither.

The [network manager](src/network/network-manager.ts) serializes adapter lifecycle operations through a single `operationTail` across adapter names; the [adapter reload state machine](src/network/adapter.ts) closes a live binding before applying a changed signature. The v12 signature includes the access token, and failed close leaves the previous config in place. These facts do not by themselves implement a poll epoch. The internal poll owner uses a gate shared by runtimes belonging to one account instance: it revokes the old owner, waits for tracked transactions before closing the queue, and blocks reactivation while cleanup remains pending or uncertain. Replacement instances have separate gates. In particular, a manager force-release after a disposal timeout can permit a replacement instance while work in the old instance remains unsettled; the current gate does not establish cross-instance exclusion for the same account. Production integration needs a reviewed manager-level barrier or an explicit new consumer-group and visible-gap policy. This seam has fake lifecycle tests but no HTTP integration; future integration must still verify credential rotation, close-failure and reopen behavior and never log credential values.

### Source admission boundary and delayed events

The existing manager selects active adapters and then schedules each `onEvent` with `Promise.resolve().then(...)`. An adapter object can be reused across a binding reload: reading only the current runtime epoch inside the later callback could admit an event selected under the old binding into the new poll queue. Capturing a ticket when the manager accepts an event addresses only delays after that capture. It does not cover earlier work: the [OneBot event pipeline](src/event-pipeline.ts) awaits metadata, backfill and conversion, and [instance dispatch](src/instance.ts) also awaits work before manager emission.

The current internal source-ticket seam defines its boundary as admission by OneBot's own pipeline, not the event's actual occurrence at QQ. After the pipeline accepting check and before asynchronous work, it captures opaque binding and online identities and carries them separately from the event. The instance checks both its current adapter and the manager's active reference, and an offline-to-online transition changes the online identity. A constructed or desired adapter alone is not proof of an active binding. Synthetic send callbacks also capture their original source generation before the asynchronous send. Missing, ineligible or stale context must not be recaptured as current merely because a listener opens later. These tickets do not include poll readiness: an event admitted before poll activation can carry the same binding and online identities as an event admitted after it. A future producer must register against the ready ordering gate at admission; a delayed callback must not acquire a new position merely because the owner became ready meanwhile.

When explicitly activated by a trusted in-process caller, the internal poll owner verifies such a ticket immediately before enqueue; missing or stale tickets still follow the existing WebSocket path without poll admission. Its `ready` result only confirms its current binding, source and ownership checks; it does not establish poll readiness, producer sequencing or gap visibility. A future readiness transition must handle both online-before-open and the usual open-before-online order, and must revalidate its identities after any synchronously reentrant callback. It uses fixed bounds of 128 events, 256 KiB of encoded array data, 64 KiB per event, eight waiters and transactions, and a ten-second maximum wait. These are neither RSS nor CPU bounds. The consumer-group lifecycle is tied to the account instance and binding/online generation, including fail-closed cleanup of uncertain prior owners. Its counters are internal and are not a user-facing loss or gap indicator. Production has no current activation caller or HTTP poll action, and the ordering and observability requirements below remain unresolved. Tickets are private provenance data, not an authentication boundary against arbitrary same-process code. The source-ticket and binding-epoch fakes do not establish QQ-side time or runtime behavior.

This boundary is deliberately limited: the [protocol packet pipeline](../protocol/src/packet-pipeline.ts) can await identity enrichment before dispatch, and the [bridge event bus](../protocol/src/event-bus.ts) synchronously invokes handlers in registration order, with each invocation reaching its first asynchronous suspension before the next is invoked; the resulting tasks are then awaited together with `Promise.allSettled`. An earlier handler can therefore synchronously reenter lifecycle code before OneBot's handler runs. Capturing at OneBot's handler says which generations were current at that admission point; it cannot prove the QQ-side occurrence time or online state before admission. Strict isolation from an earlier source boundary would require separate upstream provenance and review.

Other entries still require an explicit inventory and policy: bot status events and heartbeat events in instance dispatch, and any other direct or future manager emissions. The synthetic callbacks in [instance context](src/instance-context.ts) carry the generation captured before sending, but v12 self-sent message conversion is currently unsupported. Determine which entries can yield poll-eligible non-meta events; for each, define its own synchronous capture point or treat its provenance as unknown and exclude it from poll admission. Do not put these private tickets into event JSON, logs or network responses. Source-ticket propagation, poll owner lifecycle and concurrency limits are separate requirements; the tickets alone do not implement a poll owner.

### Event order remains unresolved

Source tickets identify an admission epoch; they do not preserve order. Event A can enter OneBot's pipeline before B, await conversion or storage, and enqueue after B. The buffer FIFO then reflects completed enqueue order, not necessarily OneBot admission order or QQ event time. The specification calls for oldest-to-newest results, so a future implementation must define the ordering basis and evaluate its conformance; this design does not claim that ordering is solved.

One possible future design is a sequencer per account and binding/online epoch. It would assign an input sequence at OneBot admission, reserve a drainable placeholder before invoking potentially reentrant handlers, and register zero or more ordered dispatch children before their first await. The parent would be sealed when it can create no more children; filtered, failed or unsupported children would need explicit terminal markers. Manager paths with no active target, rejection or asynchronous failure must also terminate the corresponding child. Synthetic self-send callbacks would retain their originally captured generation but obtain a separate sequence for each actual callback, rather than one sequence for a send action that can emit multiple events.

A sequencer needs limits on pending inputs, children, retained bytes and work per flush, plus monotonic deadlines measured from each admission. Overflow or expiry must permanently close the relevant slot, reject its late results, and make the resulting gap observable; an implementation must choose and document whether a gap degrades the epoch or permits best-effort continuation. An ordering timeout does not cancel a stuck pipeline task or guarantee hard real-time progress. It also cannot justify returning an empty short poll while an earlier eligible head remains unresolved. Reordering must feed one poll FIFO and must not make existing WS/v11 fanout await it. The [ingress sequencer](src/v12-runtime/ingress-sequencer.ts) implements a bounded, fail-closed ordering state machine with fake-only tests. An explicitly activated ordered poll-owner seam now feeds its output to the existing FIFO, validates the instance's account identity and a bounded structural subset of converted event shapes, and keeps a gap sticky for the same binding/online epoch within its instance gate. The ordered `start` can return an already-enqueued FIFO prefix through the internal transaction coordinator, but an empty or timed-out reservation returns the internal `empty_unresolved` outcome without writing an empty success. It is not connected to production producer activation or production HTTP, and `empty_unresolved` is not yet a defined client-facing HTTP response. For an ordered transaction, a committed batch that is locally known unsent or whose delivery is unknown leaves a sticky internal gap for that source epoch; the batch is not automatically replayed. A local finish is not proof of remote receipt. The structural validator does not establish event origin, QQ semantics or relationships such as whether alternative text matches the message segments. The end-to-end ordering, wakeup and visible-gap rules described here remain proposed.

A preliminary producer admission path is under development behind an internal, explicitly installed fake-fixture ready pointer. Production installs no such pointer and does not inject the HTTP capability. In a fixture context, “pre-ready” here means only an input admitted after successful preparation and before installation. When its private admission scope reaches the target runtime, that input is excluded from every later poll owner, including a legacy owner. An input admitted before successful preparation is outside that exclusion guarantee. Preparation requires an explicitly supplied runtime-module-registered target. If an originally unprepared context has an invalid preparation attempt, it remains unprepared; if the caller ignores that failure and continues, legacy completion-order behavior remains. A conflicting attempt on an already prepared context leaves its original cell and target intact. This means extending preparation to production would change legacy backfill semantics and requires explicit review. The ordered sequencer is configured for at most 128 parents, 256 children and 32 children per parent; synchronous scope stacks are limited to 32 frames per key. These are separate limits and are not total process-memory bounds. The path reserves a bounded parent before a potentially reentrant source capture, keeps admission metadata separate from event and adapter arguments, and allows existing WS/v11 fanout to proceed independently. This is not a claim that all instance lifecycle paths are connected or verified. The fixture-only preparation API accepts a context and a target supplied by trusted test code. Runtime construction registers the object in an internal WeakSet without creating a listener or enabling the feature; that registration is not an authorization mechanism. Installation compares the supplied reference directly with the exact current ordered facade in the registered runtime's private poll slot, without reading or invoking the supplied object. It rechecks the slot, gate and context after the actual owner's validity check, and does not publish a pointer if those facts change. That validity check is not side-effect-free: the existing sequencer timeout handling can record a gap and retire the owner. Revoking a context also changes its revision before a ready pointer exists. By contrast, revoking a target alone with no ready pair is not a barrier against an in-flight installation; the runtime's current `revokePoll` path also invalidates its poll owner, but future lifecycle wiring must preserve and verify the complete sequence. This seam still does not establish that the context belongs to the same instance. A production readiness barrier must establish and revalidate that association. The ordered gate is scoped to one instance; force-release followed by a replacement instance does not provide cross-instance exclusion.

Only a `NOT_ELIGIBLE` marker actually observed in a live synchronous private scope establishes that an input preceded the ready cut. If an override returns before that scope is claimed or the scope stack overflows, the fake prepared path records a loss against the input's original source: it first locks the instance gate against activation and transactions, then verifies that source. A stable verified source yields a sticky `scope_lost` gap; missing, conflicting, reentrant or otherwise unverifiable evidence leaves the stronger uncertain gate. An active legacy or ordered owner is revoked where its ownership can be established, and a later same-epoch owner cannot consume the event. Existing reservations retain their normal release and post-commit unknown handling; no committed item is replayed. Known internal meta and zero-child inputs are excluded separately and do not report this scope loss. A lost scope from a late continuation is not evidence of a new admission; it may conservatively degrade later availability, and a gate made uncertain has no automatic epoch recovery. The original Promise and WS/v11 path remain independent. This is a trusted fake-only seam, not a security boundary against arbitrary same-process code; its unproven context-to-instance association and absence of a cross-instance barrier still block production enablement.

Even a correct OneBot-admission sequencer would not establish QQ occurrence order or a globally monotonic event `time`: upstream processing can be asynchronous and timestamps can be equal or arrive late. The specification says oldest-to-newest but this design has not established which ordering basis satisfies every implementation. Source tickets alone do not supply either ordering or a complete set of events.

HTTP polls in one epoch compete for one FIFO consumer group, rather than each receiving a copy. WebSocket subscription delivery remains independent: polling must neither consume nor suppress the existing WS fanout. Conversely, WS delivery is not evidence that an HTTP event was consumed. Whether other future clients need independent groups is a separate design decision.

## Proposed transport-owned response transaction

This section specifies a future integration seam; none of it is connected today.

1. After the existing request/auth/account checks, validate `limit` and `timeout` as nonnegative safe integers, reject unsupported fields, and convert seconds to milliseconds only after checking the buffer limit and arithmetic bounds. The reviewed integration target uses one explicit maximum wait of 10 seconds; greater values produce a fixed error. The standard specifies `timeout` as an int64; this proposed cap does not support its full nonnegative range. Separately, `limit: 0` means no count limit, subject to the disclosed queue and response bounds. Establish a monotonic request deadline with a response margin beyond the bounded poll wait before reserving. Leave existing non-poll action and body deadlines unchanged; do not assume the current `Promise.race` cancels work.
2. Safely snapshot a bounded primitive echo, preserving `""` and omitting an absent value. Compute the UTF-8 bytes of the complete fixed success envelope and the JSON-encoded echo. Reserve only a batch that fits the remaining `data` array budget, also bounded by the buffer's `maxQueueBytes`; if fewer than two bytes remain, do not reserve. The configured cap applies to the complete response, not merely `eventsJson`.
3. A coordinator directly receives the buffer result and captures the exact selected token and immutable string privately. A bounded parse may verify that the captured value is a JSON array and that its count and byte length agree. Build the fixed response envelope with that trusted array **as a JSON value**, not as an escaped JSON string. Encode echo separately using JSON string encoding. Recheck the UTF-8 byte length of the final immutable response. A zero-byte output budget is fatal, not an empty success.
4. A result of `empty` or `timeout` has no token. A short poll returns `contended` rather than `empty` when an active reservation or older waiters prevent it from observing an available head; this may happen with or without queued events. `empty` describes only the instant of that queue check and does not establish reliable receipt of earlier events. Whether these outcomes should map to a successful empty array requires further review against the protocol and consumer-group fairness expectations. `blocked` has no token and leaves the head in the queue; report an explicit failure rather than an empty success. `invalid`, `busy`, `closed`, cancellation, an oversize event/batch and output-budget failure must remain distinct internally. Exact HTTP statuses and OneBot error codes/messages for these cases are pending integration review; never silently commit a fallback as though it contained the selected events.
5. On preparation or serialization failure, release any selected token before considering a fixed, sanitized failure envelope with the original echo. If even that envelope exceeds the cap, close the response. An oversized head remains queued and can block repeated polls until an explicit owner policy resolves it; do not silently drop it.
6. Before committing and before the first operation that could make headers or body externally visible, check the request generation/epoch, abort/close state and monotonic deadline. Enter a synchronous committing state and call `commit(selectedToken)` once. A false result means stale or closed: do not write the prepared response. `commit()` synchronously drains waiters and may consume time or cause reentrant effects; immediately after a successful return, recheck generation/epoch, abort/close and the monotonic deadline. If any is invalid, do not start the first write: the events are already consumed, so record local loss or unknown delivery as appropriate and never roll back or requeue them. Otherwise start the write immediately, with no intervening `await`. State transitions must handle reentrant close/abort during commit or writing and prevent a second commit or release.

This proposed **commit-before-first-write** policy chooses at-most-once queue consumption by this process, not at-most-once remote delivery. A crash, abort or synchronous write exception after commit and before any bytes leave can lose the response. A partial write, disconnect, callback error or unexpected synchronous throw after commit has an unknown delivery outcome and must not cause the token to be released or the event to be requeued. A local HTTP `finish` only indicates local write completion, not client receipt. Releasing after a partial write instead would permit duplicate delivery. A durable queue and client acknowledgements alone do not establish a delivery guarantee. A separate layered design and reliability evaluation would need to address stable event IDs, event persistence, recovery and replay, acknowledgement ordering, client idempotency or deduplication, and the associated failure windows.

A wait can become reserved just before abort, deadline or shutdown while its Promise continuation has not yet run. The continuation must still take ownership of a late token, recheck generation/abort/deadline and release it if stale. An outer timeout must not abandon the original promise without arranging this cleanup. Before commitment, first terminal transition wins and cleanup removes its listeners and timers; after commitment, abort only records the potentially unknown delivery outcome. Closing the buffer itself discards queued entries, which must be part of the chosen epoch policy.

## Review and offline verification before integration

- Verify separate account, binding and online generations, token rotation, offline-to-online, disable/reopen and close-failure behavior; old owners, source tickets and reservation tokens must not act on a new poll epoch. Pause a pipeline after admission but before manager emission, and separately pause the manager after adapter selection but before `onEvent`; cross each boundary and assert old events do not reach the new poll queue while v11/WS fanout is unchanged. Exercise earlier event-bus synchronous reentrancy, synthetic send callbacks, status, heartbeat and missing tickets under their documented policies. Check queue discard and overflow observability without recording private event bodies or credentials.
- Exercise ordering separately from epoch tickets: admit A then B, complete B before A, and verify the chosen bounded ordering policy; repeat with A filtered or failed so its tombstone unblocks B. Cover a stalled A, timeout, overflow and epoch changes without indefinite blocking, and evaluate the selected basis against oldest-to-newest semantics.
- Preserve the existing transport echo/validation/busy/handler/normalization error precedence under saturation, including response-set busy before body parsing; test duplicate JSON members with one parse and a consistent final echo. Test ordinary token one-shot behavior, owner lifecycle and cancellation independently from source tickets and concurrency admission.
- Use an in-memory Node `Writable` or equivalent deterministic fake, without `listen`, and no input-selected handler. Exercise reentrant callbacks, commit failure, duplicate terminal signals, abort before and after commit, synchronous write throws, partial writes, finish/close ordering and unknown delivery after commit. Use a fake monotonic clock that crosses the deadline during commit/drain, and trigger synchronous revoke, abort or close during commit: after a successful commit, assert that the post-commit recheck suppresses the first write, reports already-consumed local loss or unknown delivery, and never rolls back.
- Exercise a late reservation after timeout/abort/quiesce, stale Promise continuations, released and closed tokens, pending-wait and listener/timer cleanup, plus a caller that abandons a prepared reservation.
- Check empty, absent, Unicode, escaped, large and lone-surrogate echoes; exact output byte boundaries including zero; valid JSON array embedding rather than a quoted string; fallback fit and fatal fallback. Check head-too-large, full queue, invalid parameters and cancellation without silent consumption.
- Check capacity and rate/admission bounds, reserved-slot accounting and fair waiters. Ensure long polls cannot monopolize all action slots without an explicit reviewed policy. Preserve ordinary action deadlines, response normalization, authentication, 401/415 and v11/WebUI behavior.
- Any future implementation needs focused fake tests, typechecking and applicable workspace checks, followed by review of the actual transport integration. Offline tests do not establish live QQ behavior or remote delivery.
