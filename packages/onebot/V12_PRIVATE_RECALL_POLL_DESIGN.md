# Private-recall provenance fence for OneBot v12 HTTP polling

## Status and boundary

**Production scoped HTTP polling admits a restricted class of private-recall projections.** The event must have locally recorded provenance from the `friend_recall` pipeline, including a matching cache-hit message ID, exact original event and event ticket, and a valid conversion-time account identity and branded v12 candidate. After guarded WebSocket subscriber fanout is attempted, an eligible completion-order attempt may create a proof and enqueue the candidate to the current scoped HTTP owner. Failed checks, unavailable or uncertain admission, overflow and lifecycle changes can still omit it. WebSocket publication is independent and is not evidence of HTTP consumption or remote receipt. See [current polling behavior](V12_HTTP_POLL_DESIGN.md#current-http-polling-behavior) and the [runtime recall branch](src/v12-runtime/runtime.ts). Prepared/ordered attempts do not fall back to the legacy or completion-order HTTP queue, and an active ordered prototype excludes completion-order fallback. The experimental ordered owner is a separate path and does not implement this recall commit fence.

The commit fence is deliberately local. Under the trusted in-process contracts, before publishing a successful guarded queue commit the queue checks the exact protected prefix and active scope and validates each recall's original v11 event/provenance proof, exact event ticket and scope account/epoch binding. The owner separately samples its live source, gate and listener before settlement; those callback-dependent samples and the queue mutation are not one cross-layer atomic snapshot and do not authenticate QQ. A successful event response uses the corresponding immutable v12 snapshots prepared for that prefix. An original object may change after commit without retroactively revoking the committed snapshot. The fence does not extend through HTTP header or body writing, local `finish`, socket delivery, client processing, or acknowledgement. A post-commit mutation alone does not require suppressing a previously committed response. A change that is later restored before the final check is likewise not detectable by a final-state comparison; this is not a claim that the object was unchanged throughout its lifetime.

The queue is volatile and bounded, and the current HTTP owner chooses completion-order FIFO prefixes before sorting each selected batch by event `time`. The opt-in guarded modes extend the internal `EnqueueResult` type with `uncertain` and `scope_revoked`; the default legacy mode does not produce those values at runtime. A closed or rotated epoch can discard buffered data; output loss or an unknown outcome after commit is not retried or requeued. No exactly-once delivery, eventual delivery, complete event history, client-visible gap report, global chronological order, or real QQ interoperability follows from this implementation.

## Guarded primitive and production status

`EventPollBuffer` has an internal `guarded-recall` mode alongside its unchanged
legacy default. The scoped construction fixes one exact active epoch/account scope
to the queue; for a recall entry admitted through its internal proof API, it also
binds the exact event ticket and proof. It reserves physical prefixes and exposes
no-drain commit, selective prune, release and blocked-head results. Each successful
no-drain effect returns a unique frozen receipt; only that same receipt can resume
its barrier. The mode also reports cleanup uncertainty separately. Guarded queues
use a separate private frozen configuration and overflow policy, so later changes
to replaceable instance properties cannot reenter queue limit checks.

The production HTTP event-time owner creates this scoped queue and a scoped
transaction coordinator for ordinary events and qualifying private recalls. The
runtime calls the internal recall-admission seam with the exact candidate, proof
and event ticket after WebSocket fanout; the owner separately validates its scope,
self, source, gate and sampled guard before enqueue. In-memory fixtures exercise
these seams, but do not establish live QQ provenance, remote receipt or complete
ordering.

A retired scope prevents new selections and commits without treating all entries
as stale recalls; the original reservation remains releasable. Retirement must be
paired with queue shutdown or notification because the scope itself does not wake
waiters. Commit validates the exact token, frozen selection and physical prefix,
then the active scope and the entire batch before mutation. A mismatch that cannot
be explained as a stale original proof makes the whole batch uncertain instead of
authorizing deletion of ordinary entries. An already committed receipt remains
committed if the scope is retired afterwards; it is not requeued. The caller must
still validate ordinary non-recall events independently: scoped mode does not by
itself validate their account, source or schema.

## Existing evidence and admission boundary

The existing [pipeline](src/event-pipeline.ts#L482-L526) captures an internal source snapshot before its asynchronous store operation and only retains provenance for an actual cache-hit message ID. The [provenance module](src/v12-runtime/private-recall-source.ts) binds a frozen snapshot and the exact converted v11 object to the originating instance context in private maps. Its matching check inspects the original v11 object's exact own keys, enumerable data-property status and values without executing getters, and its converter creates a frozen v12 projection. It does not compare the `writable` or `configurable` flags, so changes only to those flags do not invalidate a proof. The snapshot's existing `recalledBySelf`, account, peer, sequence, time, and store-resolved signed message ID are the local evidence used by the current path. Do not re-read a later mutable QQ event, infer direction from the converted notice, or claim the snapshot proves a unique original QQ message or real QQ-side direction. Existing store matching and duplicate-recall limitations remain as documented in [the listener guide](ONEBOT_V12.md#supported-behavior-and-limits).

The current scoped admission is restricted by the following local requirements:

- The event was delivered through the qualified runtime source scope; the exact ticket for that scope is the ticket stored in the original provenance. It belongs to the current account, binding and online epoch. Missing, foreign, stale or unverified tickets do not acquire a replacement ticket.
- The exact v11 object and its provenance map entry match; the initial conversion and the immutable v12 snapshot correspond to that same evidence. A copied event, unrelated JSON object, arbitrary caller-supplied guard, or equal `message_id` is not an authority. Internal tickets and proofs are correlation mechanisms, not a security boundary against arbitrary same-process code.
- After guarded WebSocket subscriber fanout is attempted, an eligible recall may activate the first HTTP owner while its original synchronous scope is still valid. The runtime rechecks that scope, ticket, object and provenance after activation and other potentially reentrant calls, and before admission. The existing in-flight and published-attempt handling remains separate from the HTTP attempt marker; a poll admission failure does not undo the preceding v11 or WebSocket handoff.
- The queue does not retain the live `recallScopeCurrent` closure: its runtime scope stack is popped after the synchronous handoff. Instead, the queue retains an internal proof bound to the original object, exact provenance and ticket, with fixed checks used again at settlement. Scope, proof and ticket sidecars are not automatically put into event JSON, diagnostics or action responses.

The current internal five-input proof factory binds the exact original v11 object, its registered provenance, the exact ticket, the account/self, and the exact converted v12 candidate, including its own `id`. Equal values alone do not establish that candidate's origin: two distinct original events and provenances can have the same account, peer, time and message ID, and even their candidate IDs can coincide. The converter privately brands a candidate only when that exact original event and provenance are registered together; the proof factory requires the exact converter-created candidate and that exact branded event/provenance pair. A copied, independently constructed, unbranded or differently sourced candidate cannot acquire the proof even if all fields and its `id` match. Keep this association out of public DTO properties and serialization. A converter-side weak-key brand uses weak references to the original event, provenance and input self; the brand itself does not strongly retain them merely because a WebSocket DTO is retained. Other objects or DTO properties can still retain their own graphs. If the weak binding has gone away, poll proof creation fails closed. A brand-registration failure leaves the otherwise valid converted DTO available to the existing WebSocket path while making the poll proof unavailable. At enqueue, `proofFor(proof, candidate)` revalidates that same candidate object and ID and its complete own-data projection: time, type, detail and subtype, self, message ID, and direction-derived user ID. The scoped queue snapshots that exact candidate without invoking getters, rechecks its proof and scope after potentially reentrant work, and attaches the independent immutable JSON, UTF-8 byte length, proof and event ticket to the same internal Entry before publishing it to waiters. A valid proof for candidate A must not authenticate candidate B, even when their IDs or JSON happen to match. The queued Entry retains its proof and associated strong references, including while reserved; release retains them for a retained entry, whereas commit, prune, overflow eviction and close remove the queue's references with that entry. Other independently retained references can outlive it. At final commit, validate the original v11/provenance and the identity of the already-bound Entry snapshot; do not reread or reparse the mutable same-process v12 candidate. Parsing the independent immutable JSON for the existing batch time sort is not a substitute for the enqueue identity proof.

The internal proof-module check `BoundTo(proof, exactEventTicket, ownerSelf)` synchronously and without callbacks verifies the opaque proof's account binding and the **exact original event-ticket reference**. This check alone does not establish that the account is online, that the owner belongs to the current manager, or that its gate and listener are current. Separately require `sameSourceEpoch(exactEventTicket, owner.source) === 'same'` and the owner's existing current-source, binding and gate checks. `owner.source` can be a different Ticket object captured in the same binding/online epoch; requiring `owner.source === exactEventTicket` would incorrectly reject it. Reject `different` and `invalid` epoch comparisons. The scoped queue rechecks these local proof and scope bindings during its callback-free final scan, after the transaction's callback-capable owner and listener samples. This does not turn those separate live-source samples into an atomic authority.

The internal epoch/account scope primitive snapshots a validated account value and a genuine owner ticket, then compares each proof against its exact event ticket and that owner's epoch. The low-level ticket implementation is shared by direct and re-exported imports within one module graph; old tickets from a separately reloaded module instance or process are not promised to remain valid. Proof creation must still receive the exact `self` object originally supplied to conversion; the independent owner-self snapshot is for the later scope check and cannot replace that conversion identity. Scope activity means only that the exact opaque handle has not been retired. It does not prove that the ticket was issued for the stated account or context: even a genuine ticket can be paired with an unrelated synthetic account by an untrusted caller. After an offline transition, two old tickets can still compare as the same historical epoch. Distinct scopes made from the same inputs can both pass; retiring one does not revoke the others or prevent another from being created. The queue must not automatically add scope, proof or ticket sidecars to v12 event JSON or diagnostics. This does not stop a caller from putting its own data or references into an ordinary event or `echo`; existing v11 serialization and TRACE behavior are unchanged.

The current HTTP event-time owner captures and fixes an independent validated account `self` when constructing its scoped queue, failing activation when that self is unavailable. The recall-admission seam binds the proof and exact event ticket to the Entry and checks them against that owner's scope; owner, listener, manager and live online-source checks remain separate. Equal JSON or event IDs cannot identify an Entry. The source provenance context and network adapter context are distinct objects: the trusted instance lifecycle connects them rather than assuming they are the same reference or joining on account text. Merely passing an account object to `BoundTo`, or maintaining an unverified parallel FIFO, is not a substitute for those checks.

The proof is a reusable binding, not a one-shot or replay-prevention capability: repeated factory calls can produce proofs for the same source and candidate, and repeated conversion can produce another candidate with a different UUID. After attempting WebSocket fanout, the runtime records an HTTP attempt in a per-runtime `WeakMap<event, WeakSet<ticket>>` before guard, activation, proof, statistics or admission callbacks. The marker also remains for an attempt excluded by prepared/ordered mode, and an existing exact pair is not attempted again in that runtime, even if admission was unavailable, rejected or uncertain. Event and ticket are keyed by object identity: another event or another ticket object is a different pair even in the same epoch. The markers belong to that runtime object and remain effective while it and the exact weak-key identities are live. Weak keys do not themselves retain either key, and markers are not durable; other runtime state or queued proofs may retain their own references. Separate WebSocket in-flight/published handling is not a QQ-wide deduplication guarantee. None of these mechanisms establishes global event uniqueness, exactly-once delivery or idempotence.

The source verifier remains a trusted synchronous callback under the existing contract. The current production instance closure reads internal adapter/manager state and `SourceGeneration.isCurrent` synchronously ([instance](src/instance.ts), [generation](src/v12-runtime/source-ticket.ts)). Repeatedly calling a verifier that changes the generation and returns a stale `true` does not prove the original generation is current. A stronger contract against such a callback requires a separately reviewed, callback-free epoch authority; this implementation does not claim one. Production scoped polling supplies a separate trusted guard for the exact listener/token/attempt: the scoped transaction resamples it around pre-settlement checks, after the guarded effect and drain, and during response writing and local finish. The file lease used by ordinary actions and the listener guard are local lifecycle checks, not source authentication or a cross-layer atomic transaction; a callback that falsely reports current state, or changes state between samples, remains outside that guarantee. The current recall path performs callback-capable checks before the final callback-free batch scan and rechecks the bound owner/token/scope under ordinary, untampered built-ins and trusted internal runtime components. Repeated samples narrow reentry windows but do not prove uninterrupted freshness or a simultaneous state across callbacks.

## Queue representation and ownership

The production event-time [buffer](src/v12-runtime/event-poll-buffer.ts) uses the scoped guarded construction. Ordinary entries retain encoded JSON and byte length with private ordinary metadata; qualifying recall entries additionally retain their proof and exact event-ticket sidecars. The transaction parses and reorders a private copy of the selected physical FIFO prefix. A guarded commit requires the exact token and frozen selection owned by the queue, not a reconstructed equal value. JSON content, public event IDs, message IDs, and positions after sorting do not identify the original queue entry: distinct entries can have identical values or IDs. The default legacy and ordered seams remain separate from the scoped production HTTP transaction.

The scoped queue associates each admitted recall's proof with its **specific internal queue Entry** before publishing that entry to waiters. An Entry object already has natural per-enqueue object identity; a public numeric ID or UUID is unnecessary if all validation and selective removal remain within that trusted queue. A queue-external side table or an exported sorted selection would instead need to carry the exact Entry reference or an opaque per-enqueue identity. A runtime type tag must distinguish proven recall entries from ordinary entries; missing or corrupt metadata must never cause an ordinary entry to be treated as a recall and deleted.

The active token owns exactly the selected physical prefix. Drop-oldest continues to protect that prefix and may remove only the oldest unreserved tail entries under its existing count and UTF-8 byte rules. Any corresponding attestation is removed with its own entry. Commit, selective discard, overflow eviction and queue close must remove the matching metadata and references atomically with their queue effects. A release keeps metadata for entries that remain queued. A settled, cancelled or invalidated transaction must not keep a private proof or original event alive merely through its token or callback; old tokens must never address a replacement owner or queue.

While a queued proof remains reachable, its binding strongly retains the original v11 event and related local objects for revalidation; other retained proof references can independently extend their lifetime. There are at most 128 physical queued entries under the current HTTP capacity, including a reserved prefix; implementation must not create a separate unbounded retention list or leave additional references in late transactions after their entries are gone. **This is an entry-count bound, not a process RSS or CPU bound.** An original object can grow after admission; inspecting its keys can allocate and take work not covered by the 64 KiB encoded-event or 256 KiB encoded-queue budgets. Using weak references alone for the queued proof would change semantics: garbage collection could cause an otherwise unchanged queued event to fail closed. This is distinct from the converter's weak pre-admission brand, which must not itself add a strong reference from a retained WebSocket DTO to the original event. Freezing the original v11 event would change other adapters' or plugins' behavior and is not part of this design.

## Scoped guarded commit and remaining limits

The following describes the current local guarded-settlement contract and the limits that remain around it. Production uses these exact-selection and guarded-settlement primitives for qualifying recalls as well as ordinary events; it does not establish an end-to-end QQ or remote-delivery guarantee. Preserve the existing limits, request parsing, authentication, `echo`, account isolation, reservation fairness, and response deadline unless a separate change is reviewed.

1. Reserve a FIFO prefix using the existing token model, and prepare the immutable candidate body under the existing count, UTF-8 batch and complete-response budgets. The queue must bind the reservation token to its canonical selected Entry identities, immutable `eventsJson`, count and byte length; the transaction must use and verify that exact selection, not treat a mutable returned result object, an equal event ID, or a caller-supplied JSON string as authority. A mismatched or swapped result cannot be committed; release only if token ownership is still established, otherwise report uncertainty. Stable time sorting applies only to this canonical selected prefix and must derive solely from its immutable snapshots. Keep any attestation association tied to the original Entry, not the sorted index. Preparation failure releases an uncommitted reservation and follows the existing failure policy.
2. Complete all potentially reentrant owner, source, sink-readiness, abort and deadline checks. Those checks may close or replace an owner, enqueue more events, or otherwise invalidate earlier observations. Recheck ownership, gate claim, slot revision, binding and token after them. Source epoch is established under the trusted-verifier contract above.
3. On the exact token's still-protected prefix, perform a final **whole-batch**, callback-free attestation check immediately before the queue mutation. Check every recall's exact original object, recorded map/provenance identity, own data-property shape and values, expected ticket and owner epoch. A missing, mismatched, changed, accessor-bearing, proxy, or otherwise unverifiable recall cannot be committed as a valid projection. Check the identity of the Entry's already-bound immutable JSON snapshot and proof; do not reread or reparse its mutable v12 candidate. Do not execute arbitrary callbacks, getters, logger code, sink methods, `await`, or user-provided predicates between the last whole-batch check and the commit linearization point. In particular, a check of R1 followed by a reentrant check of R2 is insufficient if R2's callback can alter R1; all callback-producing checks must precede the final batch scan.
4. If all selected recalls pass, atomically commit the exact protected prefix. No other token, newly enqueued tail entry, or sorted output position may be substituted. Once committed, never release or requeue those entries for a response failure. The transaction must know the commit succeeded before any deferred waiter drain or diagnostic can report failure.
5. If a selected recall's original-binding proof is no longer current, and no scope mismatch or other uncertainty prevents settlement while the owner and token remain current, use a single token-bound, atomic prune-and-release operation: remove **only the identified recall entries**, preserve every selected ordinary and still-valid recall entry and every unselected tail entry in their prior FIFO order, update bytes and metadata, clear the reservation, then resume waiters. Do not commit the remaining entries or send a success body for that failed attempt. A well-formed `pruned` result can map to the sanitized `20002` / `poll unavailable` failure, preserving a valid request `echo` when the transport remains active, the deadline and budget permit a response, and no write has begun. A later consumer can reserve retained entries: releasing data that was neither committed nor written is not replaying a delivered response. Once the reservation is released, later admissions may still evict these unreserved entries under the configured overflow policy; preservation is a property of the prune operation, not a promise to retain them indefinitely. The owner counts a valid positive prune in `stale_pruned`, separately from overflow and post-commit uncertainty; the counter and best-effort logs are not a complete loss ledger. A still-current proof whose scope/account/ticket binding unexpectedly mismatches causes uncertainty instead of a guessed prune. In the guarded primitive, a `close()` return value only describes the close request. The scoped owner inspects `guardedCleanupState()` and keeps its gate unavailable when cleanup or ownership cannot be established, including after quarantine.
6. If an epoch, deadline, cancellation, or owner revocation wins before commit, follow the existing stop/release and retirement rules instead of describing the whole batch as bad provenance. If the token or its ownership cannot be established, do not delete entries by a guessed index. Unexpected metadata, a throwing verifier, partial queue mutation or uncertain cleanup must use an explicit conservative outcome; preserve ordinary entries when their ownership is known, and keep the existing uncertain-gate behavior when cleanup cannot be proved. If admission has already changed the queue and its later waiter drain fails, the caller must treat the admission effect as uncertain rather than infer that the entry was never inserted and automatically retry it. Normal stale-recall handling must not make a shared account gate permanently uncertain.

The legacy `PollQueue.commit(token): boolean` does not distinguish all these cases. The scoped guarded queue now exposes token- and exact-selection-bound discriminated settlement results, including committed, stale recall pruned, revoked scope and uncertain outcomes; production polling uses that guarded transaction for ordinary entries and qualifying recall entries. In guarded mode the old boolean `commit(token)` path is disabled for its reservations and fails without mutation; the default legacy/ordered modes retain their separate boolean behavior. The scoped transaction tracks a known committed, pruned, released or blocked effect separately from an unknown effect, and must not release a consumed token or treat a known committed batch as uncommitted. These local results do not establish QQ event authenticity or remote delivery.

The legacy commit removes the prefix before it drains waiters. The scoped guarded no-drain operations perform their guarded commit, targeted prune or release and establish a queue-local drain barrier before exposing the effect; the production scoped recall path uses these operations. While the barrier is set, a later short poll must not select past older waiters, and no new reservation may overtake the not-yet-drained FIFO; a live long poll may join the bounded waiter queue under the existing admission rules. Enqueue and independent v11/WS fanout need not wait, but enqueue must not bypass the barrier by draining synchronously. Each no-drain effect must return a unique immutable receipt that is the authority to resume that exact barrier. After the transaction records that receipt and any applicable counters, resume using the same receipt by identity and run the authorized FIFO drain promptly without waiting for HTTP response completion. A late, repeated, copied or foreign receipt must not release a newer barrier. Keep the barrier effective against outside reservation until that drain has completed. Clear it only after the drain or an explicit conservative failure transition, and ensure work queued during draining is not stranded. Observe drain failures and preserve whether the earlier effect was already committed, pruned or released; an actually uncertain waiter/token cleanup keeps the existing conservative gate behavior. Close, cancellation and epoch retirement must settle or revoke the barrier without granting a replacement owner access to uncertain old work.

The current [transport](src/v12-network/index.ts) distinguishes known uncommitted effects from scoped uncertainty. A valid `pruned` result or a scope revocation with a structurally known, explicitly uncommitted effect can receive `20002` / `poll unavailable` with the request echo when the response remains writable and no write was attempted; uncertain effects do not justify fabricating `data: []` success or a retry. After any header/write attempt, the transport cannot safely issue a second fallback response. Production scoped transactions retain commit-before-write for both ordinary and qualifying recall entries and additionally resample the trusted listener guard around writing and local finish; that does not make delivery atomic or revoke an already committed snapshot.

## Blocked heads, waiters and bounded progress

The current scoped buffer returns `blocked` without a token when an ordinary FIFO head exceeds a request's data budget. Its guarded primitive can instead reserve an **internal, protected single-head token** for a recall entry and settle that head after the owner's checks; it is never exposed to the HTTP client. The production scoped owner can use this primitive to prune a stale recall head; it does not guarantee progress without an eligible poll and valid lifecycle. The queue must not independently delete that head during `reserve` without the owner's trusted current-epoch authority.

After the continuation takes ownership of the token, it first checks cancellation, the response deadline, owner/source epoch and gate. If a terminal condition has already won, release or revoke the token under the existing lifecycle rules and do not prune. Otherwise, after all potentially reentrant checks, a callback-free `settleBlockedGuardedNoDrain` rechecks the exact token, Entry, proof and owner bindings: a valid recall is released unchanged and reported as `blocked`; a recall with a stale original-binding proof can be pruned only at that one head and reported as a failure. An unexplained scope/account/ticket mismatch is uncertain rather than a guessed prune. A revoked token or uncertain settlement has an explicit conservative outcome. The same no-drain receipt and `drainPending` barrier apply before resuming waiters. Cancellation, timeout and close must also settle a token selected just before its Promise continuation runs. An ordinary blocked head retains the existing blocked behavior.

This approach may not remove an ordinary entry or a valid recall merely because it exceeds this particular request's budget. A valid oversized head remains blocked; clients with inadequate budgets cannot demand progress past it. If the complete response budget is too small even for the envelope, the existing fallback may occur before any queue selection and does not prove that a stale head was cleaned. Fixed production response and event limits normally leave room for one event, but the general queue and controlled fixtures can have smaller budgets.

For pending waiters, preserve the existing precedence: a waiter whose wait deadline has expired or whose signal is aborted before selection settles as timeout or aborted before selecting or pruning on its behalf; it cannot acquire a new head or cause stale-entry deletion merely because its callback ran late. If selection occurred while the waiter was live, a continuation that observes its response deadline expired or signal aborted must first release the selected token, not prune. Expiry of the original wait interval after a timely selection is not by itself a new response deadline. A later live waiter can then use the normal guarded path. Short polls must not bypass an active reservation, `drainPending` barrier or older waiter. Bound any stale-head scan by the queue capacity and make progress explicit; do not spin, await arbitrary proof callbacks, or monopolize the shared gate. Monotonic deadline checks remain sampled deadlines, not hard real-time guarantees, and no CPU bound follows from the count limit alone.

The original reserve Promise must still be observed after timeout, abort or close. If it fulfilled with a token before its continuation ran, that continuation owns the late token and must release or settle it if still valid. Owner retirement closes the coordinator and keeps the shared gate until tracked work and its cleanup actually settle; a replacement owner must not inherit an old token, original object or proof. A cleanup outcome whose effects are genuinely uncertain may keep the gate uncertain under the existing policy; this is distinct from an ordinary invalid recall and is not an automatic recovery guarantee.

## Diagnostics and protocol limits

A well-formed positive stale-proof prune increments the separate saturating internal `stale_pruned` counter; it is distinct from oldest-drop, full rejection, shutdown discard and post-commit unknown delivery. For observed non-admission on applicable paths, the runtime can attempt the fixed warning `v12 http poll private recall event not admitted`; it is content-free and category-deduplicated. Neither the counter nor best-effort logs are a durable loss ledger, complete account of omissions, per-event prune report or client-visible gap API. Poll diagnostics must not expose message IDs, account data, event bodies, original objects, tickets, credentials or exception text, run inside the final check/commit critical section, or suppress v11/WS fanout. Existing v11 serialization and TRACE behavior are separate.

The [candidate action response specification](https://12.onebot.dev/connect/data-protocol/action-response/) uses **SHOULD** for returning a nonempty request `echo`; the current implementation also preserves a valid empty string where a response is possible. Maintain existing request preflight, echo, HTTP-only routing and error precedence. The candidate [meta-action specification](https://12.onebot.dev/interface/meta/actions/) calls for non-meta events oldest to newest. The current surviving FIFO-prefix selection followed by per-batch stable time sorting does not establish global oldest-first, cross-batch order, QQ occurrence order, or completeness. Adding this recall fence does not resolve those broader questions or turn `[]` into proof that upstream work is empty.

## Staged acceptance plan: in-memory fakes only

These are acceptance cases for the scoped production path and its local boundaries, not a claim that any particular test run or live QQ interaction has succeeded. Use synthetic events, in-memory queues, trusted fake sinks, source/gate state and a fake monotonic clock. Do not use QQ, Hook, target ELF or shared libraries, real Core startup, account plugins, OS sockets or network listeners to exercise these cases.

1. **Evidence and admission.** Real provenance capture/remember/conversion functions with synthetic store results: valid peer and self direction, signed message IDs, cache miss, wrong account or ticket, cloned original, accessor or non-enumerable own descriptors, extra symbol, getter/proxy and missing provenance. Verify no getter runs, no unqualified event is admitted, and v11/WS behavior remains independent. For two distinct registered original events A/B with the same account, peer, time and message ID, make the synthetic converter generate candidates with equal fields and equal IDs: proof creation for A's candidate with B's provenance must fail, while correctly matched candidates can obtain proofs. Also reject proof A paired with candidate B and copied or unbranded candidates. Simulate brand-registration failure and verify that the valid DTO and existing WS path remain unchanged while no poll proof is available. Check that retaining a WS DTO does not create a strong brand reference to the original v11 object; garbage-collection timing itself is nondeterministic. After a valid admission, verify that the converter-created candidate is frozen and the Entry uses its independent snapshot; a changed clone cannot substitute for that branded candidate. Exercise first-event activation and synchronous same-object/ticket reentry.
   For `BoundTo`, accept an exact event ticket and validated owner self only when they match the proof; reject a different ticket reference or account. Separately verify that distinct event and owner Ticket objects from the same binding/online epoch pass `sameSourceEpoch`, while a changed binding, changed online epoch or invalid Ticket fails. A valid proof and `BoundTo` result alone must not activate an offline, foreign-manager or otherwise invalid owner.
2. **Queue identities and mixed batches.** Select `[ordinary A, recall R1, ordinary B, recall R2]` with duplicate message IDs and shuffled times. Mutate R1 before commit. Expect only R1 pruned, failure with the original echo, A/B/R2 retained in FIFO physical order, correct byte accounting, and later eligible delivery without replay. Ensure sort output does not change proof association. Swap tokens or alter the returned JSON, count or byte length and verify that canonical reservation binding prevents commit. Exercise missing/corrupt proof without deleting an unproven ordinary entry, and verify the old boolean commit cannot bypass guarded mode while legacy behavior remains unchanged.
3. **Reentry and final batch scan.** A source/owner/sink-readiness callback changes R1 after an earlier R1 check while R2 is being inspected; the final pure whole-batch scan must catch it. A callback that closes or replaces the owner must prevent old-token mutation. Test trusted verifier exceptions separately from a deliberately stale-true fake; the latter is outside the current trusted-verifier guarantee unless a new pure epoch authority is implemented.
4. **Late reservation and overflow.** Resolve a waiter with a protected prefix but delay its continuation; enqueue enough later data to exercise count and Unicode/escaped-byte overflow. Only unreserved entries may be evicted, and each eviction removes its own proof. Mutate the reserved recall before continuation; verify its targeted prune and the exact retained ordinary entries, active token, and independent oldest-drop count. Test commit and release separately.
5. **Blocked, expired and concurrent waiters.** Use a small data budget with a stale recall at the head and ordinary data behind it; verify the internal protected-head token and guarded settlement make bounded progress without skipping a valid oversized head. Include an already-expired waiter ahead of a live waiter, an active reservation, short-poll contention, and a second consumer with a larger budget. No expired waiter may acquire a new reservation or cause pruning on its own behalf; a continuation that discovers response expiry or abort after selection releases its token without pruning. Pause after `guardedNoDrain`, enqueue more events and start another poll: `drainPending` must prevent overtaking, then one observed drain restores FIFO. Test barrier cleanup on close and a drain failure after a known commit without replay.
6. **Lifecycle and cleanup.** Abort, timeout, close, offline-to-online change, replacement and shared-gate retirement before commit, including a late fulfilled reservation. Confirm no old proof/token touches the replacement queue, retained ordinary entries are preserved when the epoch remains valid, tracked work settles, and known cleanup does not strand the gate. Test an actually uncertain cleanup as a separate fail-closed case rather than claiming normal progress.
7. **Commit boundary and failure.** After a successful guarded commit, make a fake sink's `writeHead` or `end` callback mutate the original event: the already-committed snapshot may still be sent. Simulate post-commit close, partial write and thrown sink operation; report the existing committed-unsent/unknown result and never requeue the committed entries. Before-commit rejection must not consume ordinary entries or be reported as a successful empty batch.
8. **Counters and resources.** Check stale/unknown-provenance diagnostics, eviction and closing-discard counters independently, including logger failure and reentry after the critical section. Verify queue-owned references are released when entries are removed by prune, overflow, commit or close, and that a settled cancellation drops the transaction's temporary references while release preserves proof for any entry still queued. A caller retaining a proof can independently retain its binding; GC timing is not an assertion. Check that repeated admission/read/retirement does not build an unbounded side table. Document that retained original-object size, reflection cost, QQ truth and remote delivery remain unproved.

Applicable isolated checks and typechecking should be run under the existing in-memory-only validation constraints, with their actual results reported separately. The opt-in queue assumes untampered built-ins and a finite, nondecreasing native `performance.now()`; injected clock throws and synchronous reentry are fault tests, not proof about an arbitrary clock. Guarded-mode `closed` or sticky `uncertain` takes precedence over validating a new poll's options or abort signal, unlike the existing legacy API. A fake result, successful local `finish`, or this design document alone is not proof of live QQ behavior or remote receipt.
