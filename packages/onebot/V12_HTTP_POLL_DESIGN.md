# OneBot v12 HTTP event polling: current behavior and historical design

## Current HTTP polling behavior

The account-local v12 runtime provides **partial HTTP-only** `get_latest_events` support on the existing enabled v12 listener. Ordinary `V12Dispatcher.handle()` and WebSocket action requests still return 10002 for this action, and `get_supported_actions` does not currently advertise it. The [candidate meta-action specification](https://12.onebot.dev/interface/meta/actions/) permits that omission; it does not by itself show whether HTTP polling is supported. The listener, authentication and other action paths remain separate from v11 and the existing WebUI. This is not a claim of complete OneBot 12 conformance or of live QQ interoperability.

Send a JSON `POST` to the existing `/` action endpoint, for example:

```json
{"action":"get_latest_events","params":{"limit":0,"timeout":5},"echo":"poll-1"}
```

`params` must be an object. `limit` and `timeout` default to zero, are nonnegative JavaScript safe integers, and `timeout` is in seconds with a local maximum of 10. Unsupported parameters return 10004 and invalid values, including a timeout above 10, return 10003 after ordinary preflight. Poll `echo` is limited to 4,096 UTF-16 code units; a longer value returns 10001 (`invalid action request`) after earlier preflight checks if a response remains writable. A supplied valid string, including the empty string, is preserved. `limit: 0` imposes no event-count limit but does not override queue, batch or complete-response budgets. The [candidate specification](https://12.onebot.dev/interface/meta/actions/) calls for non-meta events oldest to newest; the bounded ordering below does not establish that across all events.

HTTP polling uses the existing v12 HTTP access checks. With a nonempty token, an Authorization header takes precedence over `access_token` in the query; when the low-level transport token is empty its existing helper accepts without checking either. The account configuration has its own token requirements. Transport busy, unavailable owner, contended reservation or a head that cannot fit the response can return a failure rather than an empty array. The response body and echo also count toward the separate HTTP output limit.

The production HTTP event-time owner uses a scoped guarded [buffer](src/v12-runtime/event-poll-buffer.ts) and [transaction coordinator](src/v12-runtime/poll-transaction.ts) for ordinary converted events. Activation captures a validated account `self`, binding and online-source epoch, and creates an exact epoch/account scope; the owner separately checks its gate, current source and lifecycle. The queue's scope is an internal correlation mechanism, not authentication of QQ origin or arbitrary same-process callers. Its guarded mode alone does not admit private recall into HTTP; that separate integration remains a [proposal](V12_PRIVATE_RECALL_POLL_DESIGN.md). The stricter ordered-ingress owner is an explicit in-process prototype, not this production path.

Admission remains completion-order FIFO, with a capacity of 128 events, a 256 KiB encoded-array queue budget, a 64 KiB single-event array budget, at most eight waiters and eight tracked poll transactions. Encoded array budgets include brackets and separators, and the queue budget includes reserved entries. The transport also limits concurrent polls to `min(8, maxConcurrent - 1)`; its default `maxConcurrent` is 64. These limits do not bound process RSS, CPU or upstream work.

To admit a new event under count or byte pressure, the HTTP owner first calculates how many oldest **unreserved** events would need to be removed. An active reservation protects its fixed physical prefix. Only if removing a prefix of the unreserved tail can satisfy both limits does the owner evict those events and admit the new one; otherwise the existing queue is left intact and the new event is dropped. A rejected oversize or invalid event is a separate case. The internal legacy and ordered owners retain their default reject-new policy, not this HTTP-specific policy.

When observed, evictions and full-queue rejection attempt the respective fixed warnings `v12 http poll queue full; oldest unreserved events dropped` and `v12 http poll queue full; new event dropped`. They contain no event content, are best effort and are deduplicated by category for the listener opening. The runtime-local internal `pollOwnerStats` exposes `dropped_oldest` as a decimal string backed by an in-memory BigInt; it counts evicted queued events, not rejected new events, other omissions or delivery failures. The slot can retain this count across owner retirement and reactivation within the same runtime; it is not durable, a per-event loss ledger or a client-visible gap API, and BigInt growth is not bounded by the queue byte limit.

Other internal counters and status fields distinguish full or invalid admission, closing discard, admission uncertainty, stale-proof pruning, post-commit uncertainty and cleanup state. Numeric counters saturate; the oldest-drop BigInt is tracked separately. An admission can become uncertain after publication or eviction if a subsequent drain or accounting step fails: it must not be retried as though no queue effect occurred. That is different from a known rejection or eviction, and diagnostics are still best-effort local observations, not proof that every loss was recorded. An invalid, regressing or unreadable oldest-drop watermark causes the sampled scoped owner to fail closed and retire if it is still current; a pre-admission statistics failure can attempt the cleanup-pending warning without suppressing independent WebSocket fanout. Production HTTP does not enqueue private recalls; the generic guarded queue's stale-recall `pruned` result is not evidence that it does.

A response first selects a FIFO prefix of the surviving queue, subject to `limit` and byte budgets, then sorts only that selected prefix by `time` in stable ascending order; equal timestamps retain their selected order. In particular, `limit: 1` selects the FIFO head, not necessarily the globally oldest event. No global time order is promised across batches or for late-arriving inputs, and `time` is not proof of QQ occurrence time. A short poll or timed wait may return successful `data: []` when it did not reserve a batch; this does not prove the upstream pipeline is empty, that prior events were received, or that another reservation holds no events.

For a guarded reservation, the queue owns a frozen selection and its exact token, physical prefix, encoded entries and metadata. The transaction validates the selection's JSON, byte count and event count, and sorts a parsed copy; sorted positions and equal event IDs are not queue-entry identity. After the owner, listener, sink and deadline checks, `commitGuardedNoDrain` receives both the original token and the exact selection object. A successful no-drain commit, guarded prune, blocked-head settlement or release returns its own frozen receipt and leaves a queue-local drain barrier. The transaction records the known effect and resumes the barrier with that exact receipt by identity; a copied, stale or foreign receipt does not authorize a later barrier. Ordinary blocked heads remain queued and are reported as blocked, rather than silently skipped.

The generic guarded primitive can return `pruned` for invalidated recall evidence: this removes the identified stale recall entries without committing the remaining selected batch, and is distinct from eviction, rejection and an unknown effect. That capability does not enable recall admission in production HTTP. A well-formed `pruned` result, or a scope revocation with an explicitly uncommitted and structurally known effect, can map to `20002` / `poll unavailable` while the response is still writable and no write was attempted. A stale selection or receipt, malformed outcome, thrown settlement or uncertain cleanup does not by itself prove a clean release. Unexpected or ambiguous outcomes follow the conservative uncertainty path; for a stale drain receipt, a separately observed closed queue can instead explain the barrier's removal. The transaction preserves the known or unknown effect rather than fabricating an empty success or automatically retrying.

The owner activates only for a valid current listener and online source. An adapter can report active without a current source or poll owner, including after an opening source attempt was revoked; polling is then unavailable, and this lifecycle observation does not establish that the timing occurs on a live network. Opening, status changes, an eligible event, or a poll can attempt activation; once ready, the owner can buffer eligible events before any poll request. If an older owner is still retiring, later status, event or poll activity retries and events in the interval can be missed. Source tickets identify the binding and online generation captured by the OneBot pipeline, not QQ occurrence or a poll-readiness cut. Earlier upstream work can still be in flight and may complete later, potentially entering a matching current epoch; no backfill, complete ready-cut or cross-epoch ordering guarantee follows. Unsupported conversions, filtered events, missing or stale source tickets, and events before readiness can be omitted. Meta events are not polled. A source-qualified private recall is intentionally omitted from HTTP polling; when its own guard succeeds, its independent WebSocket publication remains possible. Other unsupported events are not necessarily published over WebSocket either.

Production HTTP also supplies a trusted listener guard tied to the exact transport, opening token and source attempt. It rechecks ownership around the file-lease/readiness and acceptance checks. The scoped transaction samples owner/epoch, sink, deadline and listener before settlement, resamples after the guarded effect and drain, and samples the listener again around response writing and local finish. These synchronous checks narrow reentry windows but rely on the trusted callbacks reporting current state; a callback that revokes state while returning stale `true`, or changes false to true between samples, is not independently authenticated by resampling. Queue-local effect ordering does not make source verification, a file lease, HTTP writing or external delivery one atomic operation. Neither this listener guard nor the ordinary-action file lease proves QQ event provenance, remote receipt, rollback of already-started effects, or protection against arbitrary same-process code.

The default `OneBotManager` factory retains a non-evicting gate for each canonical positive safe-integer UIN, up to 1,024 entries for that manager's lifetime, including accounts instantiated while polling is disabled. Invalid UINs or exhausted capacity leave polling unavailable rather than creating a replacement gate. The default factory passes the same gate to replacement instances for that UIN, so pending cleanup can block a new owner. A custom instance factory does not automatically receive this manager gate; different managers and processes do not automatically share it. This gate is not durable storage, a same-process security boundary, or a guarantee of complete event history.

Listener close, account replacement, binding or online-generation changes, and process termination can retire the in-memory owner and discard unconsumed entries. Scoped retirement revokes the scope, closes the coordinator and waits for tracked transactions before closing the queue and checking its cleanup state. A `close()` return alone is not proof that guarded cleanup completed. If cleanup, ownership or accounting cannot be established, the local gate can remain sticky-uncertain and block a replacement owner; a clean scope revocation or a known queue drop is not automatically such uncertainty. When retirement cleanup observes buffered entries being discarded, it attempts the fixed warning `v12 http poll retired with undelivered buffered events`. This is best effort and category-deduplicated, not a persistent loss count or client-visible gap.

The transaction commits a selected batch before beginning the response write. A failure after commit can lose the batch or leave remote delivery unknown; it is not requeued or automatically replayed. A known commit, an unknown queue effect, cleanup uncertainty and an unknown delivery are distinct local observations. For an observed uncertain delivery outcome the runtime attempts the fixed warning `v12 http poll delivery outcome unknown; events may be missed`, deduplicated by category for that listener opening. This best-effort warning is neither a client-visible gap notification nor proof that every loss is observed. Local HTTP `finish` is not a client acknowledgement. WebSocket fanout remains independent of the poll queue, subject to its existing source guards, and does not confirm HTTP consumption. See [the listener guide](ONEBOT_V12.md) and [SDK polling guide](../sdk/ONEBOT_V12.md#polling-events-on-a-supporting-implementation).

## Historical design snapshot: before production HTTP integration

The remainder preserves the earlier analysis, proposed stronger sequencing and verification checklist as a historical snapshot. References to production wiring and owner scope in that snapshot describe the pre-integration state unless explicitly contrasted with the current behavior above; historical legacy-token and `commit(token)` descriptions are not the current production scoped transaction API. The stricter ordered-producer and empty-result proofs remain proposals or fixture-only seams; the current HTTP endpoint uses the narrower completion-order policy above. Historical test descriptions do not establish live delivery or present test results.

### Historical code snapshot

- [OneBotManager](src/manager.ts) rejects `started` and `closed` callbacks from a superseded source binding or after disposal. If an unsubscribe throws during rebinding, the error propagates and callbacks from the uncertain old subscription remain rejected until a successful bind. For a close from the current source, the manager compares the exact Bridge object against its instance, pending-start and migration snapshots before retiring each matching binding. This does not retroactively cancel already-started work: reuse of the same Bridge object across lifecycles is not a unique generation proof, and neither check establishes cross-instance polling ownership.
- [Runtime](src/v12-runtime/runtime.ts) constructs `self` from the account context and creates a per-account `V12Dispatcher`. Its binding signature included host, port and access token. It converted supported v11 events and published them to subscribers. An explicitly activated internal [poll owner](src/v12-runtime/poll-owner.ts) could additionally enqueue events with a valid source ticket; at that point no production caller activated it for HTTP polling.
- [Dispatcher](src/v12/dispatcher.ts) snapshots JSON-shaped requests before processing. Its constructor copies `options.self` and version; an explicitly supplied `self` must be valid and match both platform and user ID. The supported-action list does not contain `get_latest_events`. The candidate [action response specification](https://12.onebot.dev/connect/data-protocol/action-response/) says a nonempty request `echo` should be returned unchanged: this is a SHOULD, not a MUST, and it does not require echoing an empty string. Jiyu preserves a supplied string `echo`, including `""`, on normal action success and failure when it can be safely observed; an absent echo is omitted. Request snapshots have explicit shape and size limits; see [validation](src/v12/validation.ts). The transport's early HTTP failures occur before an action body has been parsed and thus do not have a request echo to preserve.
- In the pre-integration snapshot, the dispatcher's internal HTTP preflight could classify poll parameters but was not yet connected to the transport and did not run a poll. For an ordinary action it freezes an opaque token and stores the private request snapshot in a WeakMap; the request snapshot itself is isolated from the original input but is not frozen. A trusted internal caller may bind a listener's file lease when creating the preflight; each ordinary token retains that exact callback and cannot substitute another when consumed. Omitting the lease keeps file-data actions fail-closed. The callback must itself correctly represent its original listener lifetime: the token does not authenticate its caller, prevent an untrustworthy callback from changing its answer, revoke unrelated ordinary actions, or cancel effects already started. Capturing the function is not a snapshot of its state; a reusable callback that changes from false back to true can revive an unconsumed token unless its owner makes retirement sticky. In particular, a callback that revokes an externally tracked lease but returns a stale `true` can permit a local store commit before a later check fails; a failed response does not establish rollback. The production runtime's own retirement also closes its generation's store, but this internal seam does not enforce an arbitrary caller's lifetime contract. Each token is consumed at most once by that dispatcher; retaining one also retains its snapshot and lease. A future owner must still establish their creation, bounded lifetime and release or invalidation separately.
- [Transport](src/v12-network/index.ts) serves HTTP and WebSocket. For an HTTP action it checks open/quiesced state, path, authentication, method, content type, response admission, request body size and UTF-8/JSON parsing. When the configured access token is nonempty, an Authorization header takes precedence over the query token; with an empty token the auth helper accepts without checking either. Defaults include 1 MiB request body, 1 MiB output, 128 connections and 15 seconds; constructor options can override them. The default 64 limit is applied separately to the HTTP `responses` set and to `active` handler dispatches shared by HTTP and WebSocket, not to their sum. These are transport defaults, not poll-buffer defaults.
- When a trusted host explicitly supplies the optional HTTP poll capability, the transport can route an admitted `get_latest_events` request to it using a guarded sink. The host remains responsible for shared preflight, readiness and ordering checks, tracking the original task, and completing all writes before its promise settles; arbitrary same-process writers are outside that contract. At that stage the default runtime supplied no capability. An [offline fixture](tests/v12-network/ordered-owner-http-bridge.fake.test.ts) now connects the actual dispatcher preflight, ordered owner and transport request handler using a test-only capability and fake request/response objects; its source readiness and account gates are synthetic. These fake tests do not establish production wiring, socket behavior, cross-instance exclusion or remote receipt.
- After the HTTP body is parsed once with `JSON.parse`, duplicate object member names have JavaScript's last-value-wins semantics. Future preflight and response echo handling must use that same parsed request, not reparse or derive different echo values. In the current transport, `requestEcho(input)` precedes the `validRequest` shape check, the `active` busy check, handler invocation (where dispatcher preflight currently runs), and response normalization. The separate HTTP `responses.size` busy check happens before reading the body, so that response has no parsed request echo. Moving detailed classification ahead of the busy check would change existing error precedence; preserve this order when integrating the HTTP preflight.
- The HTTP body-read timer is cleared after parsing; ordinary `dispatch` separately races the actual handler against its timeout. The optional poll path instead aborts and destroys its response at its deadline while continuing to observe the original task; it cannot forcibly settle a trusted host promise. Both use the configured timeout, but these are separate 15-second timers by default, not one end-to-end deadline. A standalone server also sets `headersTimeout` and `requestTimeout`; in attach mode the host owns socket and header/idle deadlines. An `active` slot is held until the underlying handler settles even when the race times out. For an ordinary action, closing a response sets the outer request as settled and cleans its bookkeeping but does not cancel the underlying action. For an injected poll capability, close or quiesce signals cancellation; an unsettled host promise can continue to occupy its active slot. `quiesce` destroys active HTTP responses and WebSocket clients.
- A v12 action response uses `status`, `retcode`, `data`, `message` and optional string `echo`. `dispatch` validates the handler response and normalizes failed responses before `json` calls `encodeResponse`; many failure messages are replaced by a fixed outcome-unknown message, while retcode and request echo are preserved. `encodeResponse` serializes the normalized object once, checks the resulting UTF-8 size and `data`, then attempts a fixed failure fallback retaining echo if needed. If the fallback exceeds the cap, ordinary action responses close the connection. HTTP errors before parsing use the same envelope when it fits, but 401/415 may instead send an empty body if the cap is too small; upgrades and destroyed connections are not universal JSON envelopes. See the [transport tests](tests/v12-network/transport.test.ts), including empty echo and serialization cases.
- The [poll buffer](src/v12-runtime/event-poll-buffer.ts) is a synchronous-enqueue/async-reserve, bounded FIFO used by the explicitly activated internal poll owner. Its `PollResult` is a mutable ordinary object; the returned token is checked by that buffer's `commit` and `release`, but there is no authenticated owner identity or special trusted result tag. After reservation, abort does not release the token; there is no active-reservation lease timer. An abandoned reservation blocks later polls. `close()` revokes the token and discards queued data; held `eventsJson` strings remain usable. Queue, batch and event limits count encoded array bytes, not the full HTTP envelope or actual process RSS. The buffer requires the owner to validate event schema, account and source epoch. Its [offline tests](tests/v12-runtime/event-poll-buffer.test.ts) described the buffer prototype and do not by themselves establish a running HTTP service.
- In this historical snapshot, the [poll transaction](src/v12-runtime/poll-transaction.ts) was used by the explicitly activated internal owner but had not yet been connected to production HTTP. It retained the bounded empty-array success for queue `empty` or `timeout` under its legacy policy. Under the ordered policy these states instead return an internal `empty_unresolved` outcome without writing a success. A timeout says only that this poll did not obtain a batch: another reservation may still hold events. Its local `finish` is not a remote acknowledgement. These are component semantics under its trusted owner and queue contracts; at that stage transport integration and consumer-group policy still needed review.

### Historical ownership and epoch analysis

Session ownership also needs an upstream identity boundary. Core's current Bridge manager removes the old Bridge before synchronously notifying a snapshot of subscribers; an earlier subscriber can reenter and start a replacement before a later subscriber receives the old close. The OneBot manager now binds each instance, migration and pending start to its exact Bridge object and only closes matching snapshots, rechecking the instance after reentrant migration cancellation. Thus a late close for a distinct old Bridge does not itself retire the replacement. This is an object-identity check, not an authenticated or unique generation token: a source that reuses the same Bridge object across lifecycles remains ambiguous. A replacement `started` callback may still be ignored while an old instance, pending start or migration is present; factory and getter reentrancy during startup also requires further review. Core exposes `getBridge(uin)`, but `BridgeSessionSource` does not require it or a generation token. At that time the account-scoped polling gate was not wired into this handoff, so that change alone did not establish a complete cross-instance polling fence. The default manager now passes a shared per-UIN gate as described above; that gate still does not establish complete upstream history.

One explicitly owned buffer/consumer group should be bound to one account and one authorization/binding epoch. A transport-owned coordinator should hold each selected token until it commits or releases it; clients and general action handlers must not receive the token or supply raw `eventsJson`. Obtaining a reservation only through that coordinator establishes its intended provenance; this is not proof that arbitrary same-process objects, modified built-ins, or hostile code are safe. The current buffer itself does not authenticate its owner. Account identity and source epoch must be validated before enqueue, since the buffer validates neither.

An internal `createPollGateRegistry(capacity)` admission container now provides a bounded, non-evicting mapping from canonical positive safe-integer account strings to local gate objects. It returns explicit invalid-account or capacity-exhausted results rather than an absent gate. Existing entries retain their exact gate and its associated private history while the registry remains live; its capacity bounds entries, not total memory or outstanding work. In the pre-integration snapshot it was not yet connected to the manager or runtime. The current default factory now supplies a per-UIN gate or explicitly disables polling on allocation failure, as described above. The registry is not a same-process isolation boundary and does not preserve state across a new registry or process; custom factory compatibility remains a separate concern.

The [network manager](src/network/network-manager.ts) serializes adapter lifecycle operations through a single `operationTail` across adapter names; the [adapter reload state machine](src/network/adapter.ts) closes a live binding before applying a changed signature. The v12 signature includes the access token, and failed close leaves the previous config in place. These facts do not by themselves implement a poll epoch. In the pre-integration snapshot the internal poll owner used a gate shared by runtimes belonging to one account instance: it revoked the old owner, waited for tracked transactions before closing the queue, and blocked reactivation while cleanup remained pending or uncertain. Replacement instances then had separate gates. A manager force-release after a disposal timeout could permit a replacement while work in the old instance remained unsettled; removing the old instance from the retiring set was not proof that disposal settled. That motivated a manager-level barrier or an explicit new consumer-group and visible-gap policy. The default factory now supplies the manager-level per-UIN gate described above, while custom factories and separate managers are not automatically coordinated. The earlier fake lifecycle and HTTP-capability fixtures do not by themselves prove credential rotation, close-failure, reopen behavior or remote delivery; credential values must not be logged.

### Source admission boundary and delayed events

The existing manager selects active adapters and then schedules each `onEvent` with `Promise.resolve().then(...)`. An adapter object can be reused across a binding reload: reading only the current runtime epoch inside the later callback could admit an event selected under the old binding into the new poll queue. Capturing a ticket when the manager accepts an event addresses only delays after that capture. It does not cover earlier work: the [OneBot event pipeline](src/event-pipeline.ts) awaits metadata, backfill and conversion, and [instance dispatch](src/instance.ts) also awaits work before manager emission.

The current internal source-ticket seam defines its boundary as admission by OneBot's own pipeline, not the event's actual occurrence at QQ. After the pipeline accepting check and before asynchronous work, it captures opaque binding and online identities and carries them separately from the event. The instance checks both its current adapter and the manager's active reference, and an offline-to-online transition changes the online identity. A constructed or desired adapter alone is not proof of an active binding. Synthetic send callbacks also capture their original source generation before the asynchronous send. Missing, ineligible or stale context must not be recaptured as current merely because a listener opens later. These tickets do not include poll readiness: an event admitted before poll activation can carry the same binding and online identities as an event admitted after it. The proposed strict sequenced producer would need to register against the ready ordering gate at admission; a delayed callback would not acquire a new position merely because the owner became ready meanwhile. This is not the current completion-order HTTP policy.

In the historical internal seam, the explicitly activated poll owner verified such a ticket immediately before enqueue; missing or stale tickets were excluded from poll admission, while WebSocket fanout followed its own source-guard policy. Its `ready` result confirmed binding, source and ownership checks, not a strict ordered-producer readiness cut, producer sequencing or gap visibility. A future readiness transition must handle both online-before-open and the usual open-before-online order, and must revalidate its identities after any synchronously reentrant callback. It uses fixed bounds of 128 events, 256 KiB of encoded array data, 64 KiB per event, eight waiters and transactions, and a ten-second maximum wait. These are neither RSS nor CPU bounds. The consumer-group lifecycle is tied to the account instance and binding/online generation, including fail-closed cleanup of uncertain prior owners. Its counters are internal and are not a user-facing loss or gap indicator. At that stage production had no activation caller or HTTP poll action. The current completion-order HTTP owner is described above; the stronger ordering and observability requirements below remain unresolved. Tickets are private provenance data, not an authentication boundary against arbitrary same-process code. The source-ticket and binding-epoch fakes do not establish QQ-side time or runtime behavior.

The source-current verifier is a trusted synchronous callback, not an independent non-reentrant generation read. If a supplied verifier computes `true` for the old generation, synchronously changes the online generation and then returns that stale `true`, calling the same callback again is not a reliable fence against the same behavior. The current production closure uses the network manager's internal `Map.get` and `SourceGeneration.isCurrent` synchronously; this observation assumes ordinary untampered in-process state and intrinsics. A side-effectful fake verifier is a trust-boundary scenario, not evidence of actual remote behavior. No protection against such a misreporting or reentrant trusted verifier is established here.

This boundary is deliberately limited: the [protocol packet pipeline](../protocol/src/packet-pipeline.ts) can await identity enrichment before dispatch, and the [bridge event bus](../protocol/src/event-bus.ts) synchronously invokes handlers in registration order, with each invocation reaching its first asynchronous suspension before the next is invoked; the resulting tasks are then awaited together with `Promise.allSettled`. An earlier handler can therefore synchronously reenter lifecycle code before OneBot's handler runs. Capturing at OneBot's handler says which generations were current at that admission point; it cannot prove the QQ-side occurrence time or online state before admission. Strict isolation from an earlier source boundary would require separate upstream provenance and review.

Other entries still require an explicit inventory and policy: bot status events and heartbeat events in instance dispatch, and any other direct or future manager emissions. The synthetic callbacks in [instance context](src/instance-context.ts) carry the generation captured before sending. V12 now projects account-matched normal group self echoes and private friend self echoes with a valid explicit `qq.target_id`. Private temporary-chat echoes and unresolved targets remain unsupported. These conversions do not themselves establish a poll admission ticket or prove delivery. Determine which entries can yield poll-eligible non-meta events; for each, define its own synchronous capture point or treat its provenance as unknown and exclude it from poll admission. Do not put these private tickets into event JSON, logs or network responses. Source-ticket propagation, poll owner lifecycle and concurrency limits are separate requirements; the tickets alone do not implement a poll owner.

### Historical proposal for strict event ordering

Source tickets identify an admission epoch; they do not preserve order. Event A can enter OneBot's pipeline before B, await conversion or storage, and enqueue after B. The buffer FIFO then reflects completed enqueue order, not necessarily OneBot admission order or QQ event time. The specification calls for oldest-to-newest results. The current HTTP implementation's selected-prefix time sort is described above; it does not solve global ordering or establish full conformance.

One possible future design is a sequencer per account and binding/online epoch. It would assign an input sequence at OneBot admission, reserve a drainable placeholder before invoking potentially reentrant handlers, and register zero or more ordered dispatch children before their first await. The parent would be sealed when it can create no more children; filtered, failed or unsupported children would need explicit terminal markers. Manager paths with no active target, rejection or asynchronous failure must also terminate the corresponding child. Synthetic self-send callbacks would retain their originally captured generation but obtain a separate sequence for each actual callback, rather than one sequence for a send action that can emit multiple events.

A sequencer needs limits on pending inputs, children, retained bytes and work per flush, plus monotonic deadlines measured from each admission. Overflow or expiry must permanently close the relevant slot, reject its late results, and make the resulting gap observable; an implementation must choose and document whether a gap degrades the epoch or permits best-effort continuation. An ordering timeout does not cancel a stuck pipeline task or guarantee hard real-time progress. Under the proposed strict guarantee, an ordering timeout would not justify returning an empty short poll while an earlier eligible head remains unresolved. The current completion-order HTTP owner makes no such empty-result proof. Reordering must feed one poll FIFO and must not make existing WS/v11 fanout await it. The [ingress sequencer](src/v12-runtime/ingress-sequencer.ts) implements a bounded, fail-closed ordering state machine with fake-only tests. An explicitly activated ordered poll-owner seam now feeds its output to the existing FIFO, validates the instance's account identity and a bounded structural subset of converted event shapes, and keeps a gap sticky for the same binding/online epoch within its instance gate. The ordered `start` can return an already-enqueued FIFO prefix through the internal transaction coordinator, but an empty or timed-out reservation returns the internal `empty_unresolved` outcome without writing an empty success. This ordered seam is not the production HTTP owner, which instead uses the completion-order policy above. When a trusted caller explicitly injects the ordered HTTP poll capability, the transport maps `empty_unresolved` to an HTTP 200 OneBot failure with retcode `20002` and message `poll unavailable`, preserving the request echo. This fail-closed injected ordered-seam behavior is distinct from the current production HTTP polling policy and is not a successful empty poll. For an ordered transaction, a committed batch that is locally known unsent or whose delivery is unknown leaves a sticky internal gap for that source epoch; the batch is not automatically replayed. A local finish is not proof of remote receipt. The structural validator does not establish event origin, QQ semantics or relationships such as whether alternative text matches the message segments. For `group_member_increase`, it permits the optional canonical string extension `qq.invitor_id` and counts it as part of the event; unknown additions remain rejected. Its JSON-number safety policy can reject an otherwise converted event whose finite timestamp exceeds the safe-integer magnitude; the ordered fixture then records an `invalid_event` gap and degrades that epoch. The end-to-end ordering, wakeup and visible-gap rules described here remain proposed.

A preliminary producer admission path is under development behind an internal, explicitly installed fake-fixture ready pointer. Production does not install this ordered-producer pointer; it now injects a separate completion-order HTTP capability. In a fixture context, “pre-ready” here means only an input admitted after successful preparation and before installation. When its private admission scope reaches the target runtime, that input is excluded from every later poll owner, including a legacy owner. An input admitted before successful preparation is outside that exclusion guarantee. Preparation requires an explicitly supplied runtime-module-registered target. If an originally unprepared context has an invalid preparation attempt, it remains unprepared; if the caller ignores that failure and continues, legacy completion-order behavior remains. A conflicting attempt on an already prepared context leaves its original cell and target intact. This means extending preparation to production would change legacy backfill semantics and requires explicit review. The ordered sequencer is configured for at most 128 parents, 256 children and 32 children per parent; synchronous scope stacks are limited to 32 frames per key. These are separate limits and are not total process-memory bounds. The path reserves a bounded parent before a potentially reentrant source capture, keeps admission metadata separate from event and adapter arguments, and allows existing WS/v11 fanout to proceed independently. This is not a claim that all instance lifecycle paths are connected or verified. The fixture-only preparation API accepts a context and a target supplied by trusted test code. Runtime construction registers the object in an internal WeakSet without creating a listener or enabling the feature; that registration is not an authorization mechanism. Installation compares the supplied reference directly with the exact current ordered facade in the registered runtime's private poll slot, without reading or invoking the supplied object. It rechecks the slot, gate and context after the actual owner's validity check, and does not publish a pointer if those facts change. That validity check is not side-effect-free: the existing sequencer timeout handling can record a gap and retire the owner. Revoking a context also changes its revision before a ready pointer exists. By contrast, revoking a target alone with no ready pair is not a barrier against an in-flight installation; the runtime's current `revokePoll` path also invalidates its poll owner, but future lifecycle wiring must preserve and verify the complete sequence. This seam still does not establish that the context belongs to the same instance. A production readiness barrier must establish and revalidate that association. In the earlier fixture the ordered gate was scoped to one instance, so force-release followed by a replacement did not provide cross-instance exclusion. The default production HTTP path now shares a per-UIN manager gate, with the narrower scope stated above.

Private recall is intentionally excluded from the runtime's internal poll delivery because the original v11 object lacks a final poll-commit guard. For a successfully converted event whose source and exact ticket remain valid, which is not a same-object/same-ticket replay, and whose ordered admission was already eligible after readiness, exclusion fails the child rather than silently skipping it. If no other terminal condition wins first, the ordered owner records a sticky `child_failed` gap for that source epoch and retires the queue; already queued but unconsumed events can also be discarded. A prior sticky gap keeps its first reason; an earlier deadline, clock or other ordering failure can therefore take precedence over `child_failed`. Missing or stale provenance, an invalid ticket, a same-object/same-ticket replay or a pre-ready admission does not by itself create this recall-specific gap; independently detected scope or ordering failures retain their own policies. Subscriber and WebSocket fanout remains separate and does not prove delivery. `pollOwnerStats` can expose internal gap state; it is not a public gap API. The legacy path never enqueues private recall and retains separate unresolved empty-result and bounded-overflow problems. The structural private-recall validator is available for direct trusted fixtures, not evidence that the runtime admits such recalls to poll. This sticky-gap description concerns the internal ordered seam, not the current completion-order HTTP owner or a completeness guarantee.

Only a `NOT_ELIGIBLE` marker actually observed in a live synchronous private scope establishes that an input preceded the ready cut. If an override returns before that scope is claimed or the scope stack overflows, the fake prepared path records a loss against the input's original source: it first locks the instance gate against activation and transactions, then verifies that source. A stable verified source yields a sticky `scope_lost` gap; missing, conflicting, reentrant or otherwise unverifiable evidence leaves the stronger uncertain gate. An active legacy or ordered owner is revoked where its ownership can be established, and a later same-epoch owner cannot consume the event. Existing reservations retain their normal release and post-commit unknown handling; no committed item is replayed. Known internal meta and zero-child inputs are excluded separately and do not report this scope loss. A lost scope from a late continuation is not evidence of a new admission; it may conservatively degrade later availability, and a gate made uncertain has no automatic epoch recovery. The original Promise and WS/v11 path remain independent. This is a trusted fake-only seam, not a security boundary against arbitrary same-process code; its unproven context-to-instance association and the then-absent cross-instance barrier prevented enabling that strict ordered path in production.

Even a correct OneBot-admission sequencer would not establish QQ occurrence order or a globally monotonic event `time`: upstream processing can be asynchronous and timestamps can be equal or arrive late. The specification says oldest-to-newest but this design has not established which ordering basis satisfies every implementation. For example, the [ordered HTTP fixture](tests/v12-network/ordered-owner-http-bridge.fake.test.ts) admits A with `time = 2` before B with `time = 1` and delivers A before B in two successive batches. This demonstrates admission FIFO, not a proof of chronological or QQ-occurrence order. Source tickets alone do not supply either ordering or a complete set of events.

A proposed empty-result proof must be a one-shot operation coordinated with the first response write, not a reusable `isEmpty()` snapshot. It would need a shared account claim and epoch, an exact ready cut, no recorded gap or uncertainty since that cut, and proof that all producers which can still affect that gate have terminated. This includes prepared inputs admitted before readiness: their eventual scope loss can degrade the later gate even when they are excluded from normal enqueue. An unprepared input is outside that exclusion guarantee. Sequencer admission, queue draining, poll entry and cleanup must be marked busy before potentially reentrant callbacks; the existing `stats()` and `running` set alone omit callback and pre-registration windows. Reservations, older waiters, pending commit/write outcomes, and prior owner result observers also need to settle or remain explicitly unresolved. A final non-reentrant authority and monotonic deadline check must share a linearization point with starting the empty write; a trusted callback that returns a stale `true` cannot itself establish that proof. These are design requirements, not implemented guarantees. Even a successful future proof would describe only a bounded observation window, not QQ-side or cross-epoch history.

HTTP polls in one epoch compete for one FIFO consumer group, rather than each receiving a copy. WebSocket subscription delivery remains independent: polling must neither consume nor suppress the existing WS fanout. Conversely, WS delivery is not evidence that an HTTP event was consumed. Whether other future clients need independent groups is a separate design decision.

### Historical proposed transport-owned response transaction

The following is the earlier proposed transaction, not a replacement for the current behavior above. The production HTTP runtime now connects the completion-order owner and transport and uses commit-before-first-write, but the stricter ordered-producer and empty-result proofs below are not established.

1. After the existing request/auth/account checks, validate `limit` and `timeout` as nonnegative safe integers, reject unsupported fields, and convert seconds to milliseconds only after checking the buffer limit and arithmetic bounds. The reviewed integration target uses one explicit maximum wait of 10 seconds; greater values produce a fixed error. The standard specifies `timeout` as an int64; this proposed cap does not support its full nonnegative range. Separately, `limit: 0` means no count limit, subject to the disclosed queue and response bounds. Establish a monotonic request deadline with a response margin beyond the bounded poll wait before reserving. Leave existing non-poll action and body deadlines unchanged; do not assume the current `Promise.race` cancels work.
2. Safely snapshot a bounded primitive echo, preserving `""` and omitting an absent value. Compute the UTF-8 bytes of the complete fixed success envelope and the JSON-encoded echo. Reserve only a batch that fits the remaining `data` array budget, also bounded by the buffer's `maxQueueBytes`; if fewer than two bytes remain, do not reserve. The configured cap applies to the complete response, not merely `eventsJson`.
3. A coordinator directly receives the buffer result and captures the exact selected token and immutable string privately. A bounded parse may verify that the captured value is a JSON array and that its count and byte length agree. Build the fixed response envelope with that trusted array **as a JSON value**, not as an escaped JSON string. Encode echo separately using JSON string encoding. Recheck the UTF-8 byte length of the final immutable response. A zero-byte output budget is fatal, not an empty success.
4. A result of `empty` or `timeout` has no token. A short poll returns `contended` rather than `empty` when an active reservation or older waiters prevent it from observing an available head; this may happen with or without queued events. `empty` describes only the instant of that queue check and does not establish reliable receipt of earlier events. At the time, whether these outcomes should map to a successful empty array required review against the protocol and consumer-group fairness expectations. The current HTTP owner returns `[]` for `empty` or `timeout` with the limited meaning described above. `blocked` has no token and leaves the head in the queue; report an explicit failure rather than an empty success. `invalid`, `busy`, `closed`, cancellation, an oversize event/batch and output-budget failure must remain distinct internally. The explicitly injected transport seam currently maps `invalid_input` and `invalid` to retcode `10003`, and `busy`, `contended`, `blocked`, `empty_unresolved`, `epoch_invalid` and `commit_rejected` to retcode `20002`, in HTTP 200 failure envelopes when the response remains writable. Those mappings were recorded for the injected seam; the current HTTP behavior is summarized above. A fallback must not be treated as though it contained selected events.
5. On preparation or serialization failure, release any selected token before considering a fixed, sanitized failure envelope with the original echo. If even that envelope exceeds the cap, close the response. A head too large for the response remains queued after that poll attempt and can block repeated polls until an explicit owner policy resolves it. This differs from the current HTTP overflow policy above, which may later evict that head while it is unreserved to admit another event.
6. Before committing and before the first operation that could make headers or body externally visible, check the request generation/epoch, abort/close state and monotonic deadline. Enter a synchronous committing state and call `commit(selectedToken)` once. A false result means stale or closed: do not write the prepared response. `commit()` synchronously drains waiters and may consume time or cause reentrant effects; immediately after a successful return, recheck generation/epoch, abort/close and the monotonic deadline. If any is invalid, do not start the first write: the events are already consumed, so record local loss or unknown delivery as appropriate and never roll back or requeue them. Otherwise start the write immediately, with no intervening `await`. State transitions must handle reentrant close/abort during commit or writing and prevent a second commit or release.

This proposed **commit-before-first-write** policy chooses at-most-once queue consumption by this process, not at-most-once remote delivery. A crash, abort or synchronous write exception after commit and before any bytes leave can lose the response. A partial write, disconnect, callback error or unexpected synchronous throw after commit has an unknown delivery outcome and must not cause the token to be released or the event to be requeued. A local HTTP `finish` only indicates local write completion, not client receipt. Releasing after a partial write instead would permit duplicate delivery. A durable queue and client acknowledgements alone do not establish a delivery guarantee. A separate layered design and reliability evaluation would need to address stable event IDs, event persistence, recovery and replay, acknowledgement ordering, client idempotency or deduplication, and the associated failure windows.

A wait can become reserved just before abort, deadline or shutdown while its Promise continuation has not yet run. The continuation must still take ownership of a late token, recheck generation/abort/deadline and release it if stale. An outer timeout must not abandon the original promise without arranging this cleanup. Before commitment, first terminal transition wins and cleanup removes its listeners and timers; after commitment, abort only records the potentially unknown delivery outcome. Closing the buffer itself discards queued entries, which must be part of the chosen epoch policy.

### Historical review and offline verification checklist

- Verify separate account, binding and online generations, token rotation, offline-to-online, disable/reopen and close-failure behavior; old owners, source tickets and reservation tokens must not act on a new poll epoch. Pause a pipeline after admission but before manager emission, and separately pause the manager after adapter selection but before `onEvent`; cross each boundary and assert old events do not reach the new poll queue while v11/WS fanout is unchanged. Exercise earlier event-bus synchronous reentrancy, synthetic send callbacks, status, heartbeat and missing tickets under their documented policies. Check queue discard and overflow observability without recording private event bodies or credentials.
- Exercise ordering separately from epoch tickets: admit A then B, complete B before A, and verify the chosen bounded ordering policy; repeat with A filtered or failed so its tombstone unblocks B. Cover a stalled A, timeout, overflow and epoch changes without indefinite blocking, and evaluate the selected basis against oldest-to-newest semantics.
- Preserve the existing transport echo/validation/busy/handler/normalization error precedence under saturation, including response-set busy before body parsing; test duplicate JSON members with one parse and a consistent final echo. Test ordinary token one-shot behavior, owner lifecycle and cancellation independently from source tickets and concurrency admission.
- Use an in-memory Node `Writable` or equivalent deterministic fake, without `listen`, and no input-selected handler. Exercise reentrant callbacks, commit failure, duplicate terminal signals, abort before and after commit, synchronous write throws, partial writes, finish/close ordering and unknown delivery after commit. Use a fake monotonic clock that crosses the deadline during commit/drain, and trigger synchronous revoke, abort or close during commit: after a successful commit, assert that the post-commit recheck suppresses the first write, reports already-consumed local loss or unknown delivery, and never rolls back.
- Exercise a late reservation after timeout/abort/quiesce, stale Promise continuations, released and closed tokens, pending-wait and listener/timer cleanup, plus a caller that abandons a prepared reservation.
- Check empty, absent, Unicode, escaped, large and lone-surrogate echoes; exact output byte boundaries including zero; valid JSON array embedding rather than a quoted string; fallback fit and fatal fallback. Check head-too-large, full queue, invalid parameters and cancellation without silent consumption.
- Check capacity and rate/admission bounds, reserved-slot accounting and fair waiters. Ensure long polls cannot monopolize all action slots without an explicit reviewed policy. Preserve ordinary action deadlines, response normalization, authentication, 401/415 and v11/WebUI behavior.
- Any future implementation needs focused fake tests, typechecking and applicable workspace checks, followed by review of the actual transport integration. Offline tests do not establish live QQ behavior or remote delivery.
