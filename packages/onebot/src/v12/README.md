# OneBot 12 core (partial, transport-independent)

This directory implements a per-account protocol translation core, not a OneBot server or a claim of full OneBot 12 conformance. The owning account lifecycle must instantiate it explicitly; no existing v11 behavior or network endpoint is changed by these modules. Reference: [action request](https://12.onebot.dev/connect/data-protocol/action-request/), [action response and codes](https://12.onebot.dev/connect/data-protocol/action-response/), [meta actions](https://12.onebot.dev/interface/meta/actions/), [meta events](https://12.onebot.dev/interface/meta/events/), [message actions](https://12.onebot.dev/interface/message/actions/), [message segments](https://12.onebot.dev/interface/message/segments/), [events](https://12.onebot.dev/connect/data-protocol/event/). OneBot 12 is a candidate standard.

## Support matrix

| Capability                                                                                     | Current core                                                                                         |
| ---------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------- |
| `get_version`, `get_status`, `get_supported_actions`                                           | Account-scoped; version and live status injected by owner                                            |
| `get_self_info`                                                                                | No parameters; validated account-local v11 login ID and nickname, with an empty `user_displayname`   |
| `get_user_info`                                                                                | Canonical uint32 string ID; one account-local v11 call; validated user fields                        |
| `get_friend_list`                                                                              | No parameters; validated account-local v11 roster, preserving order and duplicates                  |
| `get_group_info`                                                                               | Canonical string group ID; one account-local v11 call; validated ID and name projection              |
| `get_group_list`                                                                               | No parameters; validated account-local v11 group ID and name, preserving order and duplicates       |
| `send_message`                                                                                 | Private/group text; group-only `mention` and `mention_all` segments, preserving order |
| `delete_message`                                                                               | Existing account-local v11 nonzero signed 32-bit message IDs                                         |
| `set_group_name`                                                                               | Validated string group ID and name; one account-local v11 call; outcome may be uncertain on failure |
| Message events                                                                                 | V11 friend/private and normal/group text and `at`, including account-matched group self echoes; no fabricated media IDs |
| Group notices                                                                                  | Valid v11 `group_recall`, `group_decrease/leave,kick,kick_me` and `group_increase` map to v12 notices |
| Friend notices                                                                                 | Valid v11 `friend_add` maps to `notice.friend_increase` with empty subtype |
| Meta event builders                                                                            | `connect`, `heartbeat`, `status_update`; transport controls emission and ordering                    |
| Other actions                                                                                  | 10002; not passed through to v11                                                                     |
| Other segments/parameters                                                                      | Explicit unsupported result/error; never silently dropped                                            |
| `get_latest_events`, other notices, requests, private self-sent events, temporary chats, media and file APIs | Not implemented                                                                                  |
| HTTP, WebSocket, Webhook, auth, event buffering                                                | Not implemented here; transport owner must implement and test separately                             |

Jiyu echoes every supplied string `echo` unchanged, including the empty string, on success and failure. The candidate standard explicitly recommends echoing non-empty strings; Jiyu's empty-string echo is an additional compatibility behavior. In-process `handle(unknown)` rejects Proxy objects before reflection and snapshots JSON-shaped input through own data-property descriptors without evaluating getters. It rejects accessors, cycles, non-finite numbers and non-plain objects, and applies a maximum of 8192 nodes, 32 nested levels, 4096 array items or object properties and 1,048,576 UTF-16 units per string. Errors return sanitized 10001; a safely observed own data-property string `echo` is retained except when the request itself is a Proxy, whose properties are never examined.

For `send_message`, strings, single segments and segment arrays are accepted. Text keeps its existing semantics. Group `mention` requires `data.user_id` to be a canonical positive decimal string in the UIN range 1 through 4294967295: numeric values, zero, larger values, leading zeroes, signs, whitespace and `'all'` are invalid. This limit avoids truncation in the downstream uint32 UIN encoding and does not change the group target ID range. It maps in order to local v11 `{type: 'at', data: {qq: '<user_id>'}}`; `mention_all` requires empty `data` and maps to `{type: 'at', data: {qq: 'all'}}`. All segments must validate before the single v11 handler call. Private sends reject both mention types with 10005 without calling the v11 handler; this is an implementation restriction, not a statement about the standard. Segment validation is sequential: shape first (10006), unknown type (10005), extra fields on known types (10007), then required fields (10006), followed by the private-mention check (10005). A valid private mention returns immediately, so later segments do not override that unsupported result. Request snapshot and size limits apply before these checks. This passes the canonical numeric ID to the existing v11 parser; v12 does not resolve a UID itself. If the v11 resolver returns no value, the resulting element may lack a UID. The element builder passes an empty UID to the encoder, which omits this default-valued field from protobuf; a resolver that ultimately rejects aborts the send path. If that resolver returns the reserved string `'all'` for a numeric user, the existing element builder selects its mention-all path; this is a potential downstream behavior, not an assertion that the service returns that value. UID population, actual mention target, QQ rendering, permissions and successful delivery remain unverified.

A normal group `message_sent` may also be translated when the v11 sender ID exactly matches the configured account ID and the nonnegative finite time does not exceed JavaScript's safe integer maximum, a local bound for the SDK and internal poll number checks. This projects an existing self echo into the standard group message shape; it does not prove delivery or guarantee an echo for every send. Private self-sent messages remain unsupported because v11's `target_id` has no standard v12 recipient field. The mapping retains the supported v11 fields, not every v11 extra, and depends on the surrounding event admission and filtering policy. An unsupported segment fails conversion; an active internal ordered poll owner records an ordering gap rather than treating the event as intentionally skipped. This internal owner is not a production HTTP polling endpoint.

Supported event conversion requires an unmodified v11 array-format `message` and `raw_message`. It maps a v11 `at` with a canonical positive account ID to `mention`, and `at` with `qq: 'all'` to `mention_all`; `alt_message` renders them as `@<user_id>` and `@全体成员`, respectively, without inserting spaces or interpreting CQ-escaped `raw_message` as plain text. This maps the v11 representation, not independently verified QQ semantics: the upstream rich-body decoder can turn an unresolved mention UIN into zero, which the v11 converter represents as `all`. Other event types and v11 message semantics require a separately reviewed mapping. A valid v11 `group_recall` is converted to `notice.group_message_delete`, with `recall` when the author and operator match and an empty subtype otherwise. Its message ID preserves the v11 value; the upstream resolver may hash a missing sequence, so it does not prove a QQ history match. Unresolved or zero author/operator IDs are rejected. A valid v11 `group_decrease` with subtype `leave`, `kick` or `kick_me` maps to `notice.group_member_decrease`, always with an empty subtype: an absent upstream reason can default to `leave`, an unknown decrease reason can default to `kick`, and the source event or actor can be locally synthesized. The v12 mapping preserves the v11 fields rather than proving QQ-side origin, reason or time. Unresolved or zero member/operator/group IDs are rejected; other decrease subtypes, including `disband`, remain unsupported. A valid v11 `group_increase` maps to `notice.group_member_increase` with an empty subtype. A validated known independent inviter is retained as the optional string extension `qq.invitor_id`, separately from `operator_id`. A validated `invitor_id: 0` and `invitor_status: 'unknown'` omits the extension; unknown covers absent or unresolved inviter identity and does not establish that no inviter existed. Upstream admission reasons can be defaults or actor-based fallbacks, and self-join user IDs can be synthesized from account context. This translation preserves v11 fields rather than establishing QQ identity. A valid v11 `friend_add` maps to `notice.friend_increase` with an empty subtype and the v11 user ID as a string. The new-friend decoder resolves the peer UIN with a routing fallback and can use the packet header time; this translation preserves v11 fields without independently verifying QQ identity, event or time. Other known non-message v11 events return null. Unsupported/malformed mapped events throw, not a partial message. Event IDs are generated independently and are not message IDs. IDs in v12 are strings, but the current QQ/v11 service can route only canonical positive decimal safe-integer account/target IDs and canonical nonzero signed-int32 message IDs. Prefix zeroes, scientific notation and unsafe values are not normalized or rounded. The configured v12 `self` is compared exactly by platform and user_id; malformed or mismatched supplied self never reaches actions. A shared multi-account transport requires separate routing and authorization and must not treat this per-account dispatcher as a global registry.

`get_self_info` calls the account-local v11 `get_login_info` once with `{}`. Its numeric safe positive ID must match the configured self ID exactly; `user_name` is the returned nickname, even when empty, and `user_displayname` is `''` because no independent display name is available. The actual v11 login-info source may already substitute the UIN when its nickname is missing. Malformed or inconsistent results and v11 failures 1400/1404 return fixed 20001; other well-formed v11 failures and thrown errors return fixed 20002. After the awaited API result is received, the dispatcher rejects Proxy responses and data and inspects required own data properties without executing getters. JavaScript Promise resolution itself can read a returned object's `then` before that inspection; an exception there maps to 20002. These fixed core messages contain no upstream exception or account details.

`get_user_info` follows the [user action definition](https://12.onebot.dev/interface/user/actions/#get_user_info), with one locally restricted `user_id` parameter: a canonical positive decimal string in `1..4294967295`. Numbers, zero, signs, leading zeroes, whitespace and larger values are invalid. After the existing request snapshot and `self`/`echo` preflight, extra parameters return 10004 before ID validation; missing or invalid IDs return 10003. A valid request calls account-local v11 `get_stranger_info` exactly once with `{user_id: number}`, with no automatic retry. This uint32 ceiling prevents truncation in the current local wire path: `OidbUserInfoRequest.uin` is `uint_32` and Proton encodes it with `>>> 0`. The guard applies only to this v12 action; direct v11 `get_stranger_info` retains its existing input behavior, including possible truncation above uint32. It is not a global QQ ID limit or a OneBot standard limit.

After `await`, the dispatcher checks for Proxy envelopes and data before reflection, rejects arrays, and reads only own data descriptors for `status`, `retcode`, successful `data`, numeric positive safe-integer `user_id` matching the request, and primitive string `nickname` and `remark`. Each string must fit the local 1,024 UTF-16-unit limit. Empty values are preserved; unknown fields are neither enumerated nor accessed. The result is exactly `{user_id: String(id), user_name: nickname, user_displayname: '', user_remark: remark}`. An empty `user_displayname` reflects the absence of an independent source, not proof the user left it unset. The local string limit is distinct from the transport's default 1 MiB output limit; JSON encoding, field names and echo count toward that budget, so an oversized core result may become a transport error or close the connection. Thenable assimilation during `await` can execute a `then` getter before inspection. Malformed results and valid v11 failures 1400/1404 map to fixed 20001 (`invalid user info result`); other valid positive v11 failures and exceptions map to fixed 20002 (`user info unavailable`). Messages omit upstream data and exception details; transport failure-message rewriting may apply.

If v11 context lacks `getStrangerInfo`, or that provider returns null, v11 synthesizes success with the requested ID and empty nickname and remark. After profile fetch failure the provider may fall back to cached profile or friend data; three dataline pseudo-contacts bypass the network lookup. Otherwise the profile fetch may access the network, and optional enterprise profile fetching is best effort. Missing data or success does not establish user existence or friendship. A profile response without `uin` is filled with `requestedUin`; a present inconsistent `uin` is checked. Matching the projected ID therefore does not prove server-side identity. Real QQ behavior is unverified. The shared v11 handler's targeted `get_stranger_info` input, terminal response and exception diagnostics are redacted, and the contact user-profile warning omits sensitive details. This is not global log sanitization: observers receive raw v11 responses, and WebUI SSE, other services and logs may independently disclose data. V11 responses and observer semantics are unchanged.

`get_friend_list` calls the account-local v11 `get_friend_list` exactly once with `{}` and accepts no parameters. After the common preflight, a nonempty parameter object returns 10004 without a handler call. For a successful result, only a non-Proxy dense array of at most 10,000 entries is accepted. Each entry must be a non-Proxy, non-array object with own data properties: positive safe-integer number `user_id`, primitive string `nickname`, and primitive string `remark`. Each string is limited to 1,024 UTF-16 code units and their combined total across all rows to 262,144 UTF-16 code units. Any invalid or over-budget entry rejects the whole result with 20001; no rows are filtered, sorted or deduplicated. In order, entries become `{user_id: String(user_id), user_name: nickname, user_displayname: '', user_remark: remark}`; empty strings and duplicate entries remain. The empty display name reflects the lack of an independent source, not evidence that a user left it unset. These are local validation limits, not network response byte limits; the transport defaults to a separate 1 MiB output limit. JSON encoding, field names and echo also consume that budget. A successful core result may be replaced by transport error 20001, or the connection closed if the fallback with echo also exceeds the limit.

The v11 action returns `[]` when its provider is absent. Its usual provider can fall back to cached entries on fetch failure and adds up to three virtual dataline devices when their IDs are not already present. Thus this result is the v11 roster representation, not proof of real friendships or a complete live list. Like `get_self_info`, upstream data can include fallbacks. This is a read-only outcome, but the v11 implementation may load or cache data or trigger network activity.

After awaiting the v11 handler, the dispatcher checks for proxies before examining the envelope, array and rows. It uses own data-property descriptors for `status`, `retcode`, successful `data`, array length and indices, and required row fields; accessors and unknown fields are not read. JavaScript's thenable assimilation during the single `await` can itself execute a `then` getter before inspection. A malformed result or well-formed v11 failure 1400/1404 maps to fixed 20001; another well-formed failure or a thrown exception maps to fixed 20002. Core response messages contain no upstream details, and there is no automatic retry. The shared v11 handler redacts this action's terminal response and exception text in its own diagnostics, including for v11 callers; the provider's fallback warning omits exception details. Observers still receive the original response, and other services, observers or debug streams may independently inspect or disclose it. The v11 response contents are unchanged.

`get_group_info` follows the [group action definition](https://12.onebot.dev/interface/group/actions/#get_group_info) with local restrictions stricter than the standard's string ID. Its only parameter is `group_id`, a canonical positive decimal string representing a JavaScript safe integer: zero, numeric values, signs, leading zeroes, whitespace and values over `Number.MAX_SAFE_INTEGER` are invalid. After common preflight, extra keys, including `no_cache`, return 10004 before ID validation; missing or invalid IDs return 10003. Neither case invokes the handler. A valid request calls the account-local v11 `get_group_info` exactly once with `{group_id: number}`.

After `await`, the dispatcher rejects Proxy envelopes and data, arrays, inherited required properties and accessors. It inspects only own data properties `status`, `retcode`, successful `data`, numeric positive safe-integer `group_id` and string `group_name`, leaving unknown extras unread. The returned ID must equal the requested ID; the name may be empty but must not exceed 1,024 UTF-16 code units. The output is exactly `{group_id: String(requestId), group_name}`. This name limit is local, not a transport byte limit; JSON encoding, field names and echo consume the separate transport budget. Await's thenable assimilation can execute a `then` getter before the checks. Malformed results, mismatched IDs and valid v11 failures 1400/1404 return fixed 20001 (`invalid group info result`); other valid failures and exceptions return fixed 20002 (`group info unavailable`). Fixed messages do not include group IDs or exception details; no automatic retry is made. Existing transport failure-message rewriting may apply.

The v11 action defaults `no_cache` to false; a missing provider or a null provider result produces synthetic success with the original requested ID and an empty name. This proves neither group existence, actual empty name, current membership nor freshness. The provider can reuse identity cache and keeps non-member group details in a short TTL cache; upstream failures can fall back to cached or empty data, and network activity remains possible. In the non-member detail path, the upstream implementation assigns the requested ID to the returned object without checking the response's `groupInfo.uin` or `results.uin`. ID equality here validates only the v11 projection, not that the upstream response belongs to the requested group. A missing upstream detail name also becomes an empty string; its real-world frequency is unknown. Real QQ behavior is unverified. The shared v11 handler's targeted `get_group_info` input, terminal response and exception diagnostics are redacted; three related contact warnings omit sensitive details. Those contact warnings are shared with v11 `get_group_info_ex` and `get_group_detail_info` calls. Observers retain the original v11 response, and existing SSE or other component logs may still see complete data; response and observer semantics are unchanged.

`get_group_list` follows the [group action definition](https://12.onebot.dev/interface/group/actions/#get_group_list): no parameters, including no `no_cache`, and exactly one account-local v11 `get_group_list` call with `{}`. Ordinary preflight applies first, including self and echo checks: non-JSON parameters return 10001, while a nonempty valid parameter object returns 10004 without a handler call. A successful envelope must contain a dense non-Proxy array of at most 10,000 entries, each a non-Proxy, non-array object with own data properties `group_id` (positive safe-integer number) and `group_name` (string). Each name is limited to 1,024 UTF-16 units and their total to 262,144 units. The entire result is rejected on invalid or over-limit data; no entries are filtered, sorted or deduplicated. Each projects to `{group_id: String(group_id), group_name}`, preserving order, duplicates and empty names while ignoring v11 extras.

After awaiting the handler, the dispatcher checks for proxies before inspecting the envelope, array or rows, and uses only the required own data descriptors without executing accessors or enumerating extra fields. Sparse arrays and inherited required fields fail. Await can itself invoke a `then` getter before those checks. Malformed results and valid v11 failures 1400/1404 return fixed 20001 (`invalid group list result`); other valid failures and exceptions return fixed 20002 (`group list unavailable`) without upstream details or automatic retry. Result limits apply only to this layer, not network bytes. The transport defaults to a separate 1 MiB output limit; escaped JSON, field names and echo consume that budget. A successful core result may become transport error 20001 or the connection may close if the fallback with echo also exceeds the limit.

The v11 action defaults `no_cache` to false and returns `[]` without a provider. The usual provider does not refresh when `identity.groups` is nonempty; only when empty does it attempt refresh, and a failed refresh warns and falls back to the current cache. Empty, successful and cached results do not establish freshness or actual membership. When a decoded group entry lacks `groupUin`, the existing contacts provider substitutes numeric zero and can retain that entry in the identity cache; if it reaches this action, the positive-ID requirement rejects the entire list with 20001 instead of dropping that row. Its real-world frequency is unknown. The underlying service may initiate network activity. Real QQ behavior is unverified. The shared v11 handler redacts this action's terminal response and exception text in its own diagnostics, including for v11 callers, and the provider fallback warning omits exception details. The v11 response and observer semantics remain unchanged: observers and debug streams may see raw data and independently traverse or disclose it, while other layers retain their own risks.

The existing v12 transport may replace most failure messages with its generic side-effect uncertainty warning, including for these read-only actions. It preserves the retcode, subject to its existing response and connection limits. See the [user action definition](https://12.onebot.dev/interface/user/actions/#get_friend_list).

The dispatcher has an internal, currently unwired HTTP preflight seam for future integration. It shares the ordinary request snapshot and top-level checks; it does not register an action or endpoint, and `handle` still returns 10002 for `get_latest_events`. Only the transport owner should obtain the internal HTTP context; this is not a same-process security boundary. Poll parameters default to zero and accept nonnegative JavaScript safe integers; unsupported parameters return 10004, invalid values return 10003, and the implementation caps `timeout` at 10 seconds (also 10003 above the cap). The snapshot rejects non-finite numbers earlier with 10001. These limits are narrower than the standard's int64 range. Input JSON has already been parsed before this seam, so duplicate JSON keys cannot be detected here.

Ordinary preflight tokens are bound to one dispatcher instance and consumed at most once. A holder may retain an unused token indefinitely; the WeakMap offers no explicit discard or revoke operation and establishes no generation, authorization, cancellation or deadline guarantees. Before executing a prepared ordinary action, a future trusted transport must validate its generation, authorization, cancellation and deadline, and control token references and their number. Deterministic revocation requires a separate future design. The outer classification object is frozen, but `error.response` is not recursively frozen; these objects do not protect against tampering by same-process code.

The constructor snapshots the value of `options.self` before validating and retaining it. Within that value and its subtree, accessors and proxies are rejected without executing their getters or traps; evaluating the `options.self` or `options.version` properties can itself invoke an options-object getter. The current runtime supplies a plain self object. JSON-shaped extensions are copied in the snapshot and deeply frozen to protect account state; rejecting self accessors and proxies is a change for those edge cases. As `get_status` shallow-copies self, nested extension values in its response remain frozen too; this observably narrows behavior for nonstandard self extensions.

## Integration contract

`V12Dispatcher` takes `{ self, version: {impl, version}, api, getStatus, getSentMessageTime }` and `handle(unknown)` returns `Promise<V12Response>`. `api` is structurally compatible with the real per-account `ApiHandler.handle`. `getStatus` must reflect actual account state. `getSentMessageTime(id)` resolves the same account's recorded send-time estimate in Unix seconds, for example `(await messageStore.findMeta(id))?.timestamp ?? null`. `findMeta` is asynchronous and may return null; `finalizeSend` persists the receipt timestamp before returning. The Bridge uses the upstream `timestamp1` when present and otherwise a local clock fallback, while the store does not record which source was used. This timestamp is a Jiyu send-time estimate, not necessarily a QQ-confirmed time. Never generate an additional value when stored metadata is missing. For send and delete, v11 1400 maps to 10003, 1404 to 20001, and other ambiguous handler/execution errors to 20002; inconsistent status and retcode map to 20001. This does not guess a platform error from a generic v11 failure. The actual send may have completed even when action execution or subsequent timestamp lookup fails; errors explicitly say not to retry automatically. The integration must record the effect/uncertainty without logging private values and must not replay such actions.

`convertV11Event(event, self)` consumes events created by the internal v11 converter, not arbitrary plugin objects, and performs account checking before conversion. The runtime must isolate and log conversion failures without interrupting v11 event dispatch. `createConnectEvent(version)`, `createStatusUpdateEvent(self, status)` and `createHeartbeatEvent(intervalMs)` provide isolated meta frames. Connect must be the first event after WS establishment; the transport provides accurate version, status, auth, lifecycle/drain and event policies. The v12 standards require Authorization header precedence over the query token: the existing v11 auth helper has different semantics and must not be reused unchanged for a v12 listener.
