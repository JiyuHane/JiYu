# OneBot v12 HTTP event polling: future design

## Status and reference

This is a design note, not a feature announcement. `get_latest_events` is not implemented by the current v12 dispatcher, and the in-memory poll buffer is not connected to the v12 runtime or HTTP transport. No second standalone transaction prototype is planned in this phase. In particular, this document does not claim complete OneBot v12 support.

The [OneBot 12 candidate meta-action specification](https://12.onebot.dev/interface/meta/actions/) requires `get_latest_events` for HTTP: return non-meta events from oldest to newest; `limit` defaults to 0, meaning no count limit; `timeout` defaults to 0, meaning no wait, and is expressed in seconds. A bounded implementation must disclose its queue and response constraints; a bounded buffer is not an unbounded interpretation of `limit: 0`. Overflow and shutdown loss must be observable.

## Current code, not the proposed behavior

- [Runtime](src/v12-runtime/runtime.ts) constructs `self` from the account context and creates a per-account `V12Dispatcher`. Its binding signature includes host, port and access token. It converts supported v11 events and publishes them to subscribers; it does not enqueue them in the poll buffer.
- [Dispatcher](src/v12/dispatcher.ts) snapshots JSON-shaped requests before processing. Its constructor copies `options.self` and version; an explicitly supplied `self` must be valid and match both platform and user ID. The supported-action list does not contain `get_latest_events`. The candidate [action response specification](https://12.onebot.dev/connect/data-protocol/action-response/) says a nonempty request `echo` should be returned unchanged: this is a SHOULD, not a MUST, and it does not require echoing an empty string. Jiyu preserves a supplied string `echo`, including `""`, on normal action success and failure when it can be safely observed; an absent echo is omitted. Request snapshots have explicit shape and size limits; see [validation](src/v12/validation.ts). The transport's early HTTP failures occur before an action body has been parsed and thus do not have a request echo to preserve.
- [Transport](src/v12-network/index.ts) serves HTTP and WebSocket. For an HTTP action it checks open/quiesced state, path, authentication, method, content type, response admission, request body size and UTF-8/JSON parsing. When the configured access token is nonempty, an Authorization header takes precedence over the query token; with an empty token the auth helper accepts without checking either. Defaults include 1 MiB request body, 1 MiB output, 128 connections and 15 seconds; constructor options can override them. The default 64 limit is applied separately to the HTTP `responses` set and to `active` handler dispatches shared by HTTP and WebSocket, not to their sum. These are transport defaults, not poll-buffer defaults.
- The HTTP body-read timer is cleared after parsing; `dispatch` separately races the actual handler against its timeout. Both use the configured timeout, but these are separate 15-second timers by default, not one end-to-end deadline. A standalone server also sets `headersTimeout` and `requestTimeout`; in attach mode the host owns socket and header/idle deadlines. An `active` slot is held until the underlying handler settles even when the race times out. Closing a response sets the outer request as settled and cleans its bookkeeping, but does not cancel the underlying action. `quiesce` destroys active HTTP responses and WebSocket clients.
- A v12 action response uses `status`, `retcode`, `data`, `message` and optional string `echo`. `dispatch` validates the handler response and normalizes failed responses before `json` calls `encodeResponse`; many failure messages are replaced by a fixed outcome-unknown message, while retcode and request echo are preserved. `encodeResponse` serializes the normalized object once, checks the resulting UTF-8 size and `data`, then attempts a fixed failure fallback retaining echo if needed. If the fallback exceeds the cap, ordinary action responses close the connection. HTTP errors before parsing use the same envelope when it fits, but 401/415 may instead send an empty body if the cap is too small; upgrades and destroyed connections are not universal JSON envelopes. See the [transport tests](tests/v12-network/transport.test.ts), including empty echo and serialization cases.
- The [poll buffer](src/v12-runtime/event-poll-buffer.ts) is a standalone, synchronous-enqueue/async-reserve, bounded FIFO prototype. Its `PollResult` is a mutable ordinary object; the returned token is checked by that buffer's `commit` and `release`, but there is no authenticated owner identity or special trusted result tag. After reservation, abort does not release the token; there is no active-reservation lease timer. An abandoned reservation blocks later polls. `close()` revokes the token and discards queued data; held `eventsJson` strings remain usable. Queue, batch and event limits count encoded array bytes, not the full HTTP envelope or actual process RSS. The buffer requires the owner to validate event schema, account and source epoch. Its [offline tests](tests/v12-runtime/event-poll-buffer.test.ts) describe the current prototype, not a running HTTP service.

## Ownership and epochs for a future integration

One explicitly owned buffer/consumer group should be bound to one account and one authorization/binding epoch. A transport-owned coordinator should hold each selected token until it commits or releases it; clients and general action handlers must not receive the token or supply raw `eventsJson`. Obtaining a reservation only through that coordinator establishes its intended provenance; this is not proof that arbitrary same-process objects, modified built-ins, or hostile code are safe. The current buffer itself does not authenticate its owner. Account identity and source epoch must be validated before enqueue, since the buffer validates neither.

The [network manager](src/network/network-manager.ts) serializes adapter lifecycle operations through a single `operationTail` across adapter names; the [adapter reload state machine](src/network/adapter.ts) closes a live binding before applying a changed signature. The v12 signature includes the access token, and failed close leaves the previous config in place. These facts do not themselves implement a poll epoch. A future owner must explicitly invalidate old request generations on quiesce, credential or binding changes, disable and disposal, and define close-failure/reopen behavior. It must not reuse a stale owner or token for the new epoch. The actual lifetime and any discard counters need implementation and review; do not log credential values.

HTTP polls in one epoch compete for one FIFO consumer group, rather than each receiving a copy. WebSocket subscription delivery remains independent: polling must neither consume nor suppress the existing WS fanout. Conversely, WS delivery is not evidence that an HTTP event was consumed. Whether other future clients need independent groups is a separate design decision.

## Proposed transport-owned response transaction

This section specifies a future integration seam; none of it is connected today.

1. After the existing request/auth/account checks, validate `limit` and `timeout` as nonnegative safe integers, reject unsupported fields, and convert seconds to milliseconds only after checking the buffer limit and arithmetic bounds. The reviewed integration target uses one explicit maximum wait of 10 seconds; greater values produce a fixed error. The standard specifies `timeout` as an int64; this proposed cap does not support its full nonnegative range. Separately, `limit: 0` means no count limit, subject to the disclosed queue and response bounds. Establish a monotonic request deadline with a response margin beyond the bounded poll wait before reserving. Leave existing non-poll action and body deadlines unchanged; do not assume the current `Promise.race` cancels work.
2. Safely snapshot a bounded primitive echo, preserving `""` and omitting an absent value. Compute the UTF-8 bytes of the complete fixed success envelope and the JSON-encoded echo. Reserve only a batch that fits the remaining `data` array budget, also bounded by the buffer's `maxQueueBytes`; if fewer than two bytes remain, do not reserve. The configured cap applies to the complete response, not merely `eventsJson`.
3. A coordinator directly receives the buffer result and captures the exact selected token and immutable string privately. A bounded parse may verify that the captured value is a JSON array and that its count and byte length agree. Build the fixed response envelope with that trusted array **as a JSON value**, not as an escaped JSON string. Encode echo separately using JSON string encoding. Recheck the UTF-8 byte length of the final immutable response. A zero-byte output budget is fatal, not an empty success.
4. A result of `empty` or `timeout` has no token. A short poll returns `contended` rather than `empty` when an active reservation or older waiters prevent it from observing an available head; this may happen with or without queued events. `empty` describes only the instant of that queue check and does not establish reliable receipt of earlier events. Whether these outcomes should map to a successful empty array requires further review against the protocol and consumer-group fairness expectations. `blocked` has no token and leaves the head in the queue; report an explicit failure rather than an empty success. `invalid`, `busy`, `closed`, cancellation, an oversize event/batch and output-budget failure must remain distinct internally. Exact HTTP statuses and OneBot error codes/messages for these cases are pending integration review; never silently commit a fallback as though it contained the selected events.
5. On preparation or serialization failure, release any selected token before considering a fixed, sanitized failure envelope with the original echo. If even that envelope exceeds the cap, close the response. An oversized head remains queued and can block repeated polls until an explicit owner policy resolves it; do not silently drop it.
6. Before committing and before the first operation that could make headers or body externally visible, check the request generation/epoch, abort/close state and monotonic deadline. Enter a synchronous committing state and call `commit(selectedToken)` once. A false result means stale or closed: do not write the prepared response. `commit()` synchronously drains waiters and may consume time or cause reentrant effects; immediately after a successful return, recheck generation/epoch, abort/close and the monotonic deadline. If any is invalid, do not start the first write: the events are already consumed, so record local loss or unknown delivery as appropriate and never roll back or requeue them. Otherwise start the write immediately, with no intervening `await`. State transitions must handle reentrant close/abort during commit or writing and prevent a second commit or release.

This proposed **commit-before-first-write** policy chooses at-most-once queue consumption by this process, not at-most-once remote delivery. A crash, abort or synchronous write exception after commit and before any bytes leave can lose the response. A partial write, disconnect, callback error or unexpected synchronous throw after commit has an unknown delivery outcome and must not cause the token to be released or the event to be requeued. A local HTTP `finish` only indicates local write completion, not client receipt. Releasing after a partial write instead would permit duplicate delivery. A durable queue and client acknowledgements alone do not establish a delivery guarantee. A separate layered design and reliability evaluation would need to address stable event IDs, event persistence, recovery and replay, acknowledgement ordering, client idempotency or deduplication, and the associated failure windows.

A wait can become reserved just before abort, deadline or shutdown while its Promise continuation has not yet run. The continuation must still take ownership of a late token, recheck generation/abort/deadline and release it if stale. An outer timeout must not abandon the original promise without arranging this cleanup. Before commitment, first terminal transition wins and cleanup removes its listeners and timers; after commitment, abort only records the potentially unknown delivery outcome. Closing the buffer itself discards queued entries, which must be part of the chosen epoch policy.

## Review and offline verification before integration

- Verify separate account and authorization epochs, token rotation, disable/reopen and close-failure behavior; old owners, generations and tokens must not act on a new one. Check queue discard and overflow observability without recording private event bodies or credentials.
- Use an in-memory Node `Writable` or equivalent deterministic fake, without `listen`, and no input-selected handler. Exercise reentrant callbacks, commit failure, duplicate terminal signals, abort before and after commit, synchronous write throws, partial writes, finish/close ordering and unknown delivery after commit. Use a fake monotonic clock that crosses the deadline during commit/drain, and trigger synchronous revoke, abort or close during commit: after a successful commit, assert that the post-commit recheck suppresses the first write, reports already-consumed local loss or unknown delivery, and never rolls back.
- Exercise a late reservation after timeout/abort/quiesce, stale Promise continuations, released and closed tokens, pending-wait and listener/timer cleanup, plus a caller that abandons a prepared reservation.
- Check empty, absent, Unicode, escaped, large and lone-surrogate echoes; exact output byte boundaries including zero; valid JSON array embedding rather than a quoted string; fallback fit and fatal fallback. Check head-too-large, full queue, invalid parameters and cancellation without silent consumption.
- Check capacity and rate/admission bounds, reserved-slot accounting and fair waiters. Ensure long polls cannot monopolize all action slots without an explicit reviewed policy. Preserve ordinary action deadlines, response normalization, authentication, 401/415 and v11/WebUI behavior.
- Any future implementation needs focused fake tests, typechecking and applicable workspace checks, followed by review of the actual transport integration. Offline tests do not establish live QQ behavior or remote delivery.
