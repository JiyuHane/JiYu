# Jiyu account plugin host: partial compatibility

This directory contains an independent implementation of a small interoperable subset, based on the public [NapCat plugin overview](https://doc.napneko.icu/develop/plugin) and [type reference](https://doc.napneko.icu/develop/plugin/api/type). NapCatQQ is Copyright © 2024 Mlikiowa; this directory includes no NapCatQQ implementation and makes no claim of ownership or permission to redistribute it.

This directory implements the host library, not installation, updates, market actions or configuration persistence. `OneBotInstance` owns one `PluginHost` per account generation, and the authenticated WebUI can explicitly enable a manually placed local package; see [plugin compatibility](../../PLUGIN_COMPAT.md) for the integrated behavior. The owner must explicitly call `enable(id, absoluteDirectory)`. Enable executes the selected ESM code in the current Node process. There is no process, permission, resource, or network isolation and no malware scanning. Only use a plugin whose execution has been deliberately selected. Plugin code can access the process, including other account state. A unique entry URL is used for each activation, but imported dependency modules can be cached and shared between accounts. This design does not establish isolation of plugin globals or dependencies.

The owner supplies `accountId`, a state root, an actual account configuration object as `managerConfig`, its account's tracked OneBot v11 action callback, stream-action classifier, logger and optional per-plugin pending-event limit. For OneBotInstance, the intended action callback is `invokeAction`; owner must provide a matching stream classifier. Never pass a v12 handler. The supplied config is exposed by reference; callers must choose an appropriate immutable, non-secret value consistent with the compatible action context. Each plugin receives a distinct account/id data directory and `config.json` path; the library does not persist plugin config. Names must be lowercase ASCII IDs (`[a-z0-9][a-z0-9_-]*`, max 80, excluding reserved device names). `package.json` may specify a relative `.mjs` entry or `.js` with `type: module`. If `main` is absent, the first existing file among `index.mjs`, `index.js`, `main.mjs` and `main.js` is selected in that order, with the same ESM and path checks; an invalid explicit `main` never falls back. The manifest must be a regular file of at most 64 KiB; the read is itself limited to 64 KiB plus one byte. Existing entry/manifest symlinks are resolved and must remain within the selected directory. Account, plugin state and config-file symlinks are rejected. These checks do not eliminate concurrent filesystem replacement races or constrain plugin imports and writes.

`plugin_init(ctx)` is required. Optional `plugin_onevent` and `plugin_onmessage` are awaited in that order per event, the latter only for a truthy `message_type`; if the first hook fails the second is skipped. Each plugin has an event-count-bounded FIFO; `dispatch` returns accepted/dropped counts immediately. Event byte size and nesting depth are not bounded here, and cloning can allocate substantial memory or block the event loop; the queue count is not a total memory bound. Different plugins run independently. Failures are reported without exception details. `actions.call(name, params, ctx.adapterName, ctx.pluginManager.config)` routes to the provided account action callback; successful `data` values including null, false and zero are preserved; this intentionally differs from the observed NapCat behavior reported during integration, which treats those falsy values as errors. Failed results and exceptions become generic identifiable errors without action messages. Streaming actions, `core`, `oneBot`, `router`, manager methods and cross-plugin exports report unsupported; `NapCatConfig` is the limited builder described below. Arbitrary NapCat plugins are not claimed compatible. Plugin-authored logger arguments are passed to the owner's logger, so the owner must apply its logging/privacy policy.

`ctx.NapCatConfig` is an independent, immutable, data-only builder with no account, storage or network authority. Its builder object is distinct for each plugin slot, including across re-enables; code that depended on cross-slot reference equality will observe a change. This reference distinction is not a security or process-isolation boundary. Its `text`, `number`, `boolean`, `select`, `multiSelect`, `html`, `plainText`, and `combine` methods create frozen copies of JSON schema data. The display methods return `type: 'html'` or `type: 'text'`, an empty `label`, the supplied string as `default`, and a key with an `_html_` or `_text_` prefix followed by a newly generated UUID-derived suffix. This independent suffix strategy does not claim to reproduce the upstream random algorithm or guarantee collision-free identifiers. HTML is retained only as untrusted string data: the host does not parse, execute, or render it, and this is not a security boundary against plugin code. These methods previously reported unsupported; their availability alone does not establish that a real plugin can initialize or run. Optional `undefined` parameters are omitted, with falsy values preserved. Option values need not occur in the option list. `reactive` is retained as metadata only and does not enable dynamic controllers. `combine` also accepts hand-written items using the declared field set; unsupported UI types are preserved as data, never rendered as HTML. Unknown properties, undefined object values, proxies, accessors, cycles, sparse arrays, non-finite numbers, dangerous keys and non-JSON values yield `CONFIG_INVALID`. Builder output is capped at 64 KiB encoded JSON, depth 16 and 10,000 nodes, 256 combined items and 256 options; key/label/description/placeholder limits are 128/256/1024/1024 UTF-16 code units and other strings 16,384. Only builder-returned snapshots are frozen; existing plugin-owned schema objects remain mutable. These mappings and limits are Jiyu's partial compatibility policy, not a claim of byte-identical upstream behavior. Building a local schema does not itself export or persist it: a plugin must expose the existing static schema export, and the existing get/set hooks remain unchanged. The current WebUI editor accepts at most 64 fields, only the `key`, `label`, `type`, `default`, `description`, and optional `reactive: false` properties, nonempty safe keys and nonempty labels, and the `string`, `text`, `number`, and `boolean` types with additional value checks. Other reactive values remain unsupported and dynamic controllers are not enabled. A builder-produced scalar is not necessarily accepted; options, display items, and other unsupported fields can cause `CONFIG_UI_UNSUPPORTED`. The editor can show a `plainText` item only when a versioned sidecar links its original builder-created object to the current slot generation and captured full schema. Such a view is entirely read-only and does not invoke config get/set hooks; unmarked copies, unknown versions and inconsistent sidecars stay unsupported. HTML items remain unsupported by the editor. This snapshot is not a guarantee that plugin schema or state remains unchanged, and the metadata is not authentication or protection against a malicious backend or same-process plugin. It does not block legacy direct config calls or other tabs; editing other fields in a display-bearing schema needs a separate server consistency design.

Explicit host configuration calls are available only for an active plugin: `getConfigSchema(id)` returns `{ fields, source }` where source is `schema`, `ui`, or `none` (and `fields` is null for none); `getConfig(id)` returns `{ value, source: 'plugin' }`; `setConfig(id, value)` returns `{ persistence: 'plugin-managed' }`. The host reads only the static `plugin_config_schema` array, or `plugin_config_ui` when the former is absent; a present invalid schema, including a function, is not executed and returns `CONFIG_INVALID`. No schema is required for the optional `plugin_get_config(ctx)` and `plugin_set_config(ctx, value)` hooks, which are invoked only by their respective explicit calls. A missing hook returns `CONFIG_UNSUPPORTED`. These hooks have no file fallback; the host does not guarantee persistence, and a resolved setter does not establish a disk write. Values are limited here to ordinary JSON objects, stricter than the upstream unknown configuration type. Schema is limited to 64 KiB/depth 16 and config to 256 KiB/depth 32 (root depth zero); both have 10,000-node limits. Copies reject proxies, accessors, cycles, dangerous keys, sparse arrays, non-finite numbers, non-JSON values and non-ordinary prototypes. Numbers use JavaScript's finite `Number` representation: raw JSON number spelling and precision are not retained after parsing, and plugin-returned numbers already reflect JavaScript rounding. The accepted JSON copies and their UTF-8 encoded bytes are bounded before dispatch, but those limits do not bound an already-constructed input object or the transient allocation and work of `Reflect.ownKeys` enumeration. They do not impose CPU or RSS limits. Same-process plugins have the process's full permissions, including network access, and can block the host; these checks provide neither a network sandbox nor resource isolation. Render schema strings as text, not HTML.

`getConfigGeneration(id)` synchronously returns an opaque, randomly generated identity for the current active, accepting slot, and null during initialization, stopping, cleanup failure, after shutdown, or when absent. A newly created slot gets a fresh identity, including after disable/re-enable and across host instances for the same account. Owners may bind configuration drafts to this identity and recheck it around asynchronous work; it is not a credential, persistence guarantee, or isolation boundary, and checks do not undo side effects after a hook has started.

Config admission is synchronous and appends to the same per-plugin FIFO as previously admitted events. Separate configurable per-plugin limits (`maxPendingConfig`, default 32, and `maxPendingConfigBytes`, default 1 MiB) cover running and queued config calls and their copied setter inputs; events retain their separate count bound. `CONFIG_QUEUE_FULL`, `CONFIG_INVALID`, `PLUGIN_INACTIVE`, and `CONFIG_REENTRANT` identify host-side rejection; no raw plugin exception, cause, paths or values are returned. Once a hook starts, exceptions or invalid getter output report `CONFIG_OUTCOME_UNKNOWN`: side effects may already have happened and are not undone or retried. While an event or config hook runs, same-slot config calls and disable, and shutdown of that slot's host, reject with `CONFIG_REENTRANT` before changing host state. While init or cleanup runs, lifecycle calls (`enable`, `disable`, `shutdown`) on that same host reject before admission or state changes. Execution tokens expire when their hook settles, so detached work retaining an old async context is not rejected merely for that stale context. Other hosts are not rejected by these identity checks. Cross-plugin and cross-host dependency cycles remain unknown and can still deadlock. A hung hook keeps its queue reservation and leaves drain pending; there is no execution deadline or forced cancellation. These guarantees do not prevent same-process plugin code from changing shared process state or interfering with host execution.

`disable` and `shutdown` stop this host's new event admission, await already admitted hooks, and call `plugin_cleanup` if present. Disabling while an enable is in progress invalidates that enable. If cancellation is observed before import, plugin code is not run; an already-started import can execute top-level code, but a cancellation observed after import prevents init. A running init finishes and cleanup is attempted before `DISABLED` is reported; later enable attempts may proceed. Already executed top-level code and its side effects are not rolled back. After admitted hooks drain, the host closes the plugin action gate and drains all actions already started through its context; on the first cleanup it temporarily permits actions, closes the gate when cleanup settles, and drains those actions too. A retry after failed cleanup never reopens action access. A never-resolving hook, registered action, or cleanup leaves drain pending. The host does not terminate timers, workers, child processes, independent external activity or unload ESM modules. Even successful cleanup leaves process resources unknown. Do not use cleanup completion to authorize overwriting a plugin program directory. Updates need cross-account coordination and a restart or independently terminable execution environment. `listStatuses()` returns only controlled IDs, states (`initializing`, `active`, `stopping`, `cleanup_failed`), cleanup/initialization failure flags, `pendingActions`, and `processResources: 'unknown'`; a missing entry is not evidence that process resources stopped. Cleanup failures retain their slot and deny new events and plugin actions. Repeating `disable(id)` or `shutdown()` retries only remaining cleanup; successful cleanup is not repeated. A failed shutdown keeps the host closed and can be retried; a pending cleanup may never settle. On init failure with cleanup failure, `enable` rejects with `CLEANUP_FAILED` and the retained status reports `initializationFailed`. The owning instance intends to quiesce action ingress before draining events and invoking cleanup, so any new action from a draining hook or cleanup may be rejected as closed. A standalone host does not itself quiesce the injected action API on ordinary disable; after cleanup failure, however, it permanently closes that plugin context's action access even during retries. Keep account stores available until host drain and cleanup succeed; on failure preserve stores for diagnostics or retry. `stateRoot` is a trusted owner-supplied root, including its ancestors; the host resolves it and does not validate its ancestor symlinks. The owner must enforce its own root policy.
