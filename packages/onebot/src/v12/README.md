# OneBot 12 core (partial, transport-independent)

This directory implements a per-account protocol translation core, not a OneBot server or a claim of full OneBot 12 conformance. The owning account lifecycle must instantiate it explicitly; the v12 additions do not change existing v11 behavior or v11 network endpoints. Reference: [action request](https://12.onebot.dev/connect/data-protocol/action-request/), [action response and codes](https://12.onebot.dev/connect/data-protocol/action-response/), [meta actions](https://12.onebot.dev/interface/meta/actions/), [meta events](https://12.onebot.dev/interface/meta/events/), [message actions](https://12.onebot.dev/interface/message/actions/), [message segments](https://12.onebot.dev/interface/message/segments/), [events](https://12.onebot.dev/connect/data-protocol/event/). OneBot 12 is a candidate standard.

## Support matrix

The Jiyu-specific `notice.qq.group_name_change` extension projects the v11 `notify/group_name` group ID and untrimmed name. Its optional `operator_id` is present only for a resolved v11 user ID; numeric positive zero (`+0`) means unresolved, not proven absence of an operator, while negative zero and the string `"0"` are rejected. Names are nonempty and limited locally to 1,024 UTF-16 units. Time follows the existing nonnegative finite safe-number rule; zero can be an upstream missing-timestamp fallback. The generic SDK event parser does not validate these extension-specific fields. Neither the projection nor a source ticket independently proves the original QQ event, identity, time or delivery.

The [candidate meta-action specification](https://12.onebot.dev/interface/meta/actions/) permits `get_supported_actions` to omit `get_latest_events`, so that omission alone does not establish whether HTTP polling is supported.

For accepted requests, Jiyu echoes every supplied string `echo` unchanged, including the empty string, on success and failure. The candidate standard explicitly recommends echoing non-empty strings; Jiyu's empty-string echo is an additional compatibility behavior. In-process `handle(unknown)` rejects Proxy objects before reflection and snapshots JSON-shaped input through own data-property descriptors without evaluating getters. It rejects accessors, cycles, non-finite numbers and non-plain objects, and applies a maximum of 8192 nodes, 32 nested levels, 4096 array items or object properties and 1,048,576 UTF-16 units per string. Errors return sanitized 10001; a safely observed own data-property string `echo` within that string limit is retained. A longer echo is omitted rather than truncated, and properties of a Proxy request are never examined. HTTP polling additionally applies a 4,096 UTF-16-unit echo limit and the transport's separate byte limits.

For `send_message`, strings, single segments and segment arrays are accepted. Text keeps its existing semantics. Group `mention` requires `data.user_id` to be a canonical positive decimal string in the UIN range 1 through 4294967295: numeric values, zero, larger values, leading zeroes, signs, whitespace and `'all'` are invalid. This limit avoids truncation in the downstream uint32 UIN encoding and does not change the group target ID range. It maps in order to local v11 `{type: 'at', data: {qq: '<user_id>'}}`; `mention_all` requires empty `data` and maps to `{type: 'at', data: {qq: 'all'}}`. All segments must validate before the single v11 handler call. Private sends reject both mention types with 10005 without calling the v11 handler; this is an implementation restriction, not a statement about the standard. After request checks and basic target parsing, a multi-segment message containing an image is rejected with 10005 by an earlier combination scan, before per-segment validation. On the non-image path validation is sequential: shape first (10006), unknown type (10005), extra fields on known types (10007), then required fields (10006), followed by the private-mention check (10005). A valid private mention returns immediately, so later segments do not override that unsupported result. Request snapshot and size limits apply before these checks. This passes the canonical numeric ID to the existing v11 parser; v12 does not resolve a UID itself. If the v11 resolver returns no value, the resulting element may lack a UID. The element builder passes an empty UID to the encoder, which omits this default-valued field from protobuf; a resolver that ultimately rejects aborts the send path. If that resolver returns the reserved string `'all'` for a numeric user, the existing element builder selects its mention-all path; this is a potential downstream behavior, not an assertion that the service returns that value. UID population, actual mention target, QQ rendering, permissions and successful delivery remain unverified.

**Outbound local-upload image.** Private and group sends accept exactly one `{type: 'image', data: {file_id}}` object, either directly or in a one-element array. In the account runtime the ID must be a canonical `jiyu-upload:v1:` handle returned by `upload_file` data mode for this account and current listener generation; incoming image/voice handles, legacy IDs, URLs, local paths, multiple images and mixed segments are unsupported. After image-shape and canonical handle checks, both private and group image targets must be canonical positive uint32 IDs; larger IDs return 10003 before local-store access or submission. The private bound protects the downstream message routing UIN; the group bound prevents narrowing in the image-upload pre-application field. Group text and location keep their existing target range. The local data must decode canonically to 1–262,144 bytes and match the returned SHA-256; an otherwise valid one-byte upload passes these checks, which do not establish image decodability or QQ acceptance. Empty uploads remain valid for data retrieval, but not image sending. Sending does not consume the handle or renew its TTL.

Image dispatch requires an explicit original listener lease, current readiness, a pinned local reader and the sensitive v11 message method; direct core dispatch without them fails closed. Checks rely on trusted callbacks to report state correctly. At most four image operations run per dispatcher from before the read through the actual send and sent-time lookup; an HTTP timeout does not release the slot early, and separate dispatchers do not share this limit. The built-in `ApiHandler` checks a one-shot start guard and quiescence after synchronous input/debug logging calls return and before starting the registered handler. It calls that handler at most once. A sensitive capability returning without the guard having granted produces 20002 with an unknown outcome, even if it claims success; this does not prove that custom code respected the guard or caused no effects. Once started, a close cannot retract effects. Unknown outcomes are not automatically resent as a whole, though existing lower-level Highway chunk handling may retry chunks.

For this sensitive path, `ApiHandler` diagnostics and action-observer records are redacted locally; observer `retcode` is only a 0/100 classification, and `handler_response: 'reported'` records a reported top-level status, not delivery. Other logs, Bridge/media sinks and same-process callbacks can still see content; caller-supplied `echo` follows the usual return rules. JavaScript string erasure is not guaranteed, and observer Promise rejection handling is best effort rather than isolation from malicious constructors/species, arbitrary thenables or asynchronous logger-subscriber failures. See the [full image-send contract](../../ONEBOT_V12.md#sending-a-single-local-upload-image).

**Outbound location.** Following the [location segment definition](https://12.onebot.dev/interface/message/segments/#location), the local v12 send path accepts a location in a private or group conversation only when it is the entire message: either a single segment object or an array containing exactly one segment. Its exact shape is `{type: 'location', data: {latitude: number, longitude: number, title: string, content: string}}`; extra segment or data fields are unsupported. Both coordinates must be finite, with latitude in `[-90, 90]` and longitude in `[-180, 180]`, inclusive. Both strings may be empty; their combined UTF-8 length is at most 64 KiB (65,536 bytes). This is a limit on those two strings, not on the serialized card or transport envelope. The ranges, length and exclusive combination are local support policies, not OneBot standard assertions. `get_supported_actions` lists action names, not segment-level capabilities. Apart from the restricted single local-upload image path described above, outbound voice and other media remain unsupported.

After ordinary request and target preflight, missing, invalid, out-of-range or over-budget location data returns 10006; extra segment or data fields return 10007. A location combined with text, mentions or another location returns 10005 without calling v11 when the segments pass their earlier checks. For these non-image combinations validation remains sequential, so earlier invalid fields can return 10006 or 10007 instead, and a valid private mention can return 10005 before later segments are examined. Snapshot and transport checks precede these results; for example, a non-finite in-process number is rejected by snapshot validation with 10001.

The dispatcher calls the account-local v11 handler once with `{type: 'location', data: {lat: latitude, lon: longitude, title, content}}`. The existing v11 parser converts coordinates with JavaScript `String`, constructs a `com.tencent.map` / `LocationShare` JSON card with `meta.Location` containing string `lat`, string `lng`, `title` and `address: content`, and the existing element builder encodes it as a `lightApp`. Thus `-0` becomes `"0"`, small coordinates may use exponent notation, and JSON number spelling and precision beyond binary64 are not preserved. No claim is made about QQ client receipt, display, readability or delivery.

The existing inbound rich-body decoder drops all sibling ordinary text in the same element list after successfully decoding a card, including independently authored text. Mixed outbound location messages therefore remain disallowed rather than relying on a lossless round trip. Incoming QQ JSON cards are still unsupported by v12 conversion and have no automatic reverse mapping to `location`. The v11 handler's existing TRACE input and observers can see coordinates, title and address in the clear; the WebUI debug tap and other paths may also expose them. A send-log preview of `[JSON消息]` is not end-to-end redaction. A failed or timed-out send may already have taken effect; no automatic retry is made when the result is uncertain. Existing v11 message behavior is unchanged.

A normal group `message_sent` may also be translated when the v11 sender ID exactly matches the configured account ID and the nonnegative finite time does not exceed JavaScript's safe integer maximum, a local bound for the SDK and internal poll number checks. This projects an existing self echo into the standard group message shape; it does not prove delivery or guarantee an echo for every send. For a private friend self echo, a visible valid v11 `target_id` is preserved in the optional nonstandard string extension `qq.target_id` because the standard private event has no recipient field. The target may equal the account ID; this projection makes no claim about whether that conversation exists. The existing v11 converter can omit such a target, so preservation only applies when v11 actually provides it. Missing, invalid, inherited, hidden or accessor targets remain unsupported rather than being guessed. A safely observed, canonical `sender.user_id` that contradicts the account rejects the echo; absent or uninspectable sender metadata remains unknown and is not evaluated. Private temporary-chat self echoes are also unsupported. The mapping retains the supported v11 fields, not every v11 extra, and depends on the surrounding event admission and filtering policy. An unsupported segment fails conversion; an active internal ordered poll owner records an ordering gap rather than treating the event as intentionally skipped. This ordered owner is a separate prototype, not the production HTTP polling owner.

Supported event conversion requires an unmodified v11 array-format `message` and `raw_message`. It maps a v11 `at` with a canonical positive account ID to `mention`, and `at` with `qq: 'all'` to `mention_all`; `alt_message` renders them as `@<user_id>` and `@全体成员`, respectively, without inserting spaces or interpreting CQ-escaped `raw_message` as plain text. This maps the v11 representation, not independently verified QQ semantics: the upstream rich-body decoder can turn an unresolved mention UIN into zero, which the v11 converter represents as `all`. Other event types and v11 message semantics require a separately reviewed mapping. A valid v11 `group_recall` is converted to `notice.group_message_delete`, with `recall` when the author and operator match and an empty subtype otherwise. Its message ID preserves the v11 value; the upstream resolver may hash a missing sequence, so it does not prove a QQ history match. Unresolved or zero author/operator IDs are rejected. A valid v11 `group_decrease` with subtype `leave`, `kick` or `kick_me` maps to `notice.group_member_decrease`, always with an empty subtype: an absent upstream reason can default to `leave`, an unknown decrease reason can default to `kick`, and the source event or actor can be locally synthesized. The v12 mapping preserves the v11 fields rather than proving QQ-side origin, reason or time. Unresolved or zero member/operator/group IDs are rejected; other decrease subtypes, including `disband`, remain unsupported. A valid v11 `group_increase` maps to `notice.group_member_increase` with an empty subtype. A validated known independent inviter is retained as the optional string extension `qq.invitor_id`, separately from `operator_id`. A validated `invitor_id: 0` and `invitor_status: 'unknown'` omits the extension; unknown covers absent or unresolved inviter identity and does not establish that no inviter existed. Upstream admission reasons can be defaults or actor-based fallbacks, and self-join user IDs can be synthesized from account context. This translation preserves v11 fields rather than establishing QQ identity. A valid v11 `friend_add` maps to `notice.friend_increase` with an empty subtype and the v11 user ID as a string. The new-friend decoder resolves the peer UIN with a routing fallback and can use the packet header time; this translation preserves v11 fields without independently verifying QQ identity, event or time. Other known non-message v11 events return null from `convertV11Event`; the runtime's source-qualified private recall path is separate. Unsupported or malformed events mapped by `convertV11Event` throw, not a partial message. Event IDs are generated independently and are not message IDs. IDs in v12 are strings, but the current QQ/v11 service can route only canonical positive decimal safe-integer account/target IDs and canonical nonzero signed-int32 message IDs. Prefix zeroes, scientific notation and unsafe values are not normalized or rounded. The configured v12 `self` is compared exactly by platform and user_id; malformed or mismatched supplied self never reaches actions. A shared multi-account transport requires separate routing and authorization and must not treat this per-account dispatcher as a global registry.

Supported incoming ordinary images require a current internal source ticket and the observed v11 public JSON shape `{type:'image',data:{file,url,sub_type,summary}}`, with string `file`, nonempty HTTP(S) `url`, `sub_type:0`, and `summary` equal to `''` or `'[图片]'`. Supported incoming voice is limited to source-qualified friend/private or normal/group messages with the exact v11 public JSON shape `{type:'record',data:{file,url}}`, where `file` is a string (including empty) and `url` is a nonempty HTTP(S) string. At this boundary required fields must be own enumerable data properties; extra visible fields, accessors and proxies are rejected. Private non-enumerable metadata is not projected or treated as provenance. Message-array elements are read from own data descriptors, including non-enumerable indices as in JSON arrays; custom iterators and index getters are not invoked. For v12 text and `at` conversion, accessors and proxies used for `type`, `data`, `text` or `qq` are rejected rather than invoked; this tightens earlier same-process accessor behavior but does not alter v11 dispatch.

Each accepted record projects lossily to `{type:'voice',data:{file_id}}` only; its local `alt_message` text is `[语音]`, while an accepted image uses `[图片]`. Before invoking a media issuer, the account-local runtime validates required event data, all supported segment shapes and every media URL's syntax and size. Direct trusted callers of `convertV11Event` need an equivalent `validateMediaFileUrl` preflight to obtain that runtime-specific URL check; the callback is optional at the core seam. Text, mentions, images and voices retain their order, and image/voice issuers run in source order. Issuers also validate each URL; a later issuance failure exposes no partially converted event but does not undo earlier issuer side effects. Flash, marketplace faces, other image subtypes or summaries, v11 `audio` and video segments, self-sent image or voice echoes, voice sends and image send modes other than the restricted local-upload path remain unsupported. This does not change v11 dispatch. Source tickets and observed URLs do not independently prove QQ origin, file identity or file bytes.

Before issuing any handle for an incoming v12 event containing images or voice, the account-local runtime enforces a combined maximum of 128 image/voice segments and 256 KiB (262,144 bytes) across their UTF-8 URLs. Exceeding either limit fails the entire conversion without truncation; an already-prepared internal ordered-prototype admission records an ordering gap under its existing rules. The production completion-order HTTP owner can omit the failed event. Text-only events and v11 behavior are unaffected by these media limits. These are local workload policies, not QQ or OneBot protocol limits, and do not bound total CPU use or process RSS. If an issuer or provider subsequently fails after reserving a nonce, that nonce is not rolled back.

This boundary is neither a lossless conversion nor a no-network guarantee for the entire pipeline. A real `OneBotInstance` normally performs existing v11 RKey and voice PTT resolution before event construction; the resolver may access the network or change the source element, and upstream decoding or v11 conversion may drop other segments or semantics such as format and duration. Existing v11 file-ID logic remains unchanged. When the v11 media URL population step throws, that particular resolver catch uses a fixed warning template with redacted exception details; other paths may still disclose data.

For ordinary converted events, production HTTP polling admits eligible events in completion order, subject to the bounded queue's eviction policy, and sorts each selected surviving FIFO prefix by event time; image and voice projections additionally verify their original source before poll admission. It then fences WebSocket fanout when the event carries an internal source ticket: it rechecks the exact runtime scope and the instance's current listener binding/online epoch before publishing and for each subscriber, snapshotting subscription generations. An unverifiable, foreign or expired provided ticket suppresses that v12 fanout; independent unticketed dispatch remains on the legacy path and v11 is unchanged. The ticket is a correlation marker rather than an authentication boundary. This check relies on a synchronous verifier that does not return a stale result after changing its own state; it does not retroactively revoke an already committed poll result, fence earlier protocol processing, prevent a same-epoch client that joined before publication from receiving a prior event, or cancel an async subscriber already invoked. A same-object/same-payload synchronous reentry can inherit the outer ticket scope.

The account-local runtime may separately project an upstream `friend_recall` to `notice.private_message_delete`. It requires an explicit boolean `recalledBySelf` on the originating upstream event, matching account, peer and event time between that source and the v11 event, and the exact `sourceTicket` captured for the same event to remain current. The same instance's message store must already have matched an existing candidate, and the v11 event must retain its nonzero signed 32-bit `message_id`; negative values are valid. Missing or tampered provenance, cloned or modified events, expired or mismatched tickets, and store misses skip this v12 event without changing normal v11 behavior. Calling `convertV11Event(event, self)` with a standalone or copied v11 `friend_recall` is not sufficient to establish the required source evidence. The source ticket is an internal correlation marker, not an authentication boundary against other code in the same process.

The source direction selects `user_id`: the account when `recalledBySelf` is true, the peer when false. The output uses an empty `sub_type` and preserves the v11 message ID as a string. The existing store selects a candidate using only peer, client sequence, direction and recall time, with a stored timestamp no later than the recall time. Its existing recall-time validation requires a nonnegative safe integer, so the store path rejects fractional recall times even though the source/conversion checks permit fractions in the normal v12 time range. This does not establish global uniqueness or identify the original QQ message. If multiple stored candidates satisfy the same peer, client sequence, direction and recall-time criteria, successive calls handling the same recall may select and remove different historical message IDs. The tombstone upsert alone does not guarantee idempotence. This is existing store behavior, not evidence that QQ sends duplicate recalls. The direction remains dependent on the existing QQ decoder and has not been verified against a real client; neither this mapping nor a local store hit establishes QQ-side success.

After final source and event revalidation, the runtime may publish this notice through v12 subscriber and WebSocket fanout; publication does not establish client delivery. The original v11 object has no final poll-commit guard, so private recall is not enqueued for production HTTP polling or the internal ordered prototype. The HTTP owner attempts a fixed warning when it observes this omission. When a successfully converted input still has its valid original source and exact ticket, is not a same-object/same-ticket replay, and has an already-ready ordered-eligible admission, its child is failed rather than silently skipped. Source-current checks trust a synchronous verifier; repeating a callback that changes the online generation and returns stale `true` is not a reliable fence. The production closure uses internal synchronous state checks; a side-effectful fake callback does not establish remote behavior. If no other terminal condition wins first, the internal owner records a sticky `child_failed` gap for that source epoch and retires its queue; previously queued but unconsumed data may be discarded too. A prior sticky gap keeps its first reason; an earlier deadline, clock or other ordering failure can therefore take precedence over `child_failed`. Missing or stale source, invalid ticket, same-object/same-ticket replay and pre-ready input do not by themselves create this recall-specific gap; unrelated ordering failures retain their own policies. This sticky gap is specific to the ordered prototype, not the production HTTP owner, which uses completion-order admission and omits private recall. `pollOwnerStats` exposes ordering state internally, not through a public gap API. The poll owner's structural validator remains available for direct trusted fixtures; that does not establish runtime poll admission or an end-to-end completeness guarantee.

`get_self_info` calls the account-local v11 `get_login_info` once with `{}`. Its numeric safe positive ID must match the configured self ID exactly; `user_name` is the returned nickname, even when empty, and `user_displayname` is `''` because no independent display name is available. The actual v11 login-info source may already substitute the UIN when its nickname is missing. Malformed or inconsistent results and v11 failures 1400/1404 return fixed 20001; other well-formed v11 failures and thrown errors return fixed 20002. After the awaited API result is received, the dispatcher rejects Proxy responses and data and inspects required own data properties without executing getters. JavaScript Promise resolution itself can read a returned object's `then` before that inspection; an exception there maps to 20002. These fixed core messages contain no upstream exception or account details.

`get_file` supports the [URL retrieval mode](https://12.onebot.dev/interface/file/actions/#get_file) for account-local cached image or voice IDs and transient v12 image or voice handles. The opaque `file_id` must be a nonempty string of at most 4,096 UTF-16 units; a non-reserved legacy ID is forwarded unchanged in one call to the existing v11 `get_file` action. It requires a well-formed success envelope and own data-property strings `file_name` (at most 1,024 units) and `url` (at most 8,192 units). The URL must be a well-formed Unicode string with an explicit HTTP(S) scheme, `://`, a nonempty raw authority, complete hexadecimal percent escapes, and no raw ASCII whitespace/control characters, backslash or userinfo. The original string is returned, not a normalized or fetched URL; syntactic checks do not guarantee that every HTTP client interprets it identically. Empty or well-formed non-HTTP(S) URLs return 10004; invalid IDs or parameter types return 10003, and malformed responses return 20001. Backend failures use fixed 20001 or 20002 responses; no provider error text is exposed. Thenable assimilation can execute a `then` getter before post-await reflection. Legacy IDs must come from the same account's v11 media path or another source and hit that account's image/voice cache. Supported incoming ordinary images and records may instead provide transient handles, described below. A cached label equal to `.` or `..`, or containing `/` or NUL, is projected as an empty unknown `name` because it is not a Linux filename; other labels are retained but may not be original filenames. Callers must validate names for their own platform before using them as filesystem paths. The OneBot standard's URL mode requires the application to be able to download the file. Jiyu's best-effort syntactic check does not establish that requirement, reachability, permission, lifetime or required headers; the returned query may contain sensitive credentials. Action-handler get_file request/terminal logs are redacted and the image-refresh warning omits its exception, while observers and lower-level logging or configured refresh services can still see data. The URL itself is intentionally returned to the caller; this is not full file-API or live QQ compatibility.

**Local data capability.** The account runtime installs callbacks that create a local store lazily; the independent core alone does not. The account runtime lists `upload_file` in `get_supported_actions` only when both data callbacks exist and the current listener upload lease is valid. An independent core with no readiness callback instead uses the presence of both callbacks. Listing an action does not imply support for all its types. `upload_file` accepts only `type: 'data'`, a primitive string `name` of at most 4,096 UTF-16 units (empty is allowed), and a canonical padded RFC 4648 Base64 string `data` representing at most 256 KiB (262,144) raw bytes. Padding is required where applicable, pad bits must be canonical, and the empty string represents zero bytes. Optional `sha256` is omitted when absent, not supplied as `undefined`; when supplied it is exactly 64 lowercase hexadecimal characters matching the raw bytes. Other upload types, including `url`, `path` and unknown types, return 10004; the separate `upload_file_fragmented` action remains unimplemented and returns 10002.

Successful local upload commits bytes in memory and returns `{file_id}`: `jiyu-upload:v1:` plus 32 random bytes encoded as unpadded base64url. A holder with access to the same account and active listener generation may use `get_file` with `type: 'data'` to retrieve `{name, data, sha256}`; `data` is canonical Base64, and `sha256` is the lowercase digest of the bytes. The original name is retained, not sanitized as a filesystem path. When the data capability is available and common ID type/length validation passes, foreign, expired and forged reserved-prefix data IDs return a local not-found result without a v11 lookup. For that prefix URL mode returns 10004 without fallback. A pre-existing v11 alias beginning with the upload prefix is consequently shadowed through v12 URL lookup, while direct v11 remains unchanged. Other image, voice and v11 URL paths retain their existing behavior. Public request snapshot and ID validation may reject earlier with 10001 or 10003.

The listener retains at most 32 entries and 4 MiB (4,194,304) raw bytes; exhaustion is a fixed failure without eviction. Expiry is 10 minutes from the upload's initial valid local clock sample, including subsequent processing; extreme delays can make an entry expire by the time success is returned. Reads do not renew expiry. Cleanup is lazy, so idle expired content may remain until the next store access or close. Only active IDs are checked for random collisions; a historical ID could in principle coincide with a new random ID. Every listener close attempt, even a failed close, the current listener token's `onError`, token/port reload, and runtime quiesce/force-close invalidate the corresponding handles. A listener lease is rechecked around synchronous callbacks and before commit. Post-bind transport errors attempt quiescence first; the runtime checks the read-only transport state at the guarded points, so a quiesced transport rejects data access, including after reentrant callbacks. If close or quiesce throws while open is pending, or construction reports an error and the existing lifecycle later restores the listener as active, the retired upload lease stays invalid and discovery omits `upload_file`; a successful close followed by reopen is needed to restore it. A peer disconnect by itself does not prove listener-generation revocation; a lost response after commit does not undo the entry or prove receipt. Local buffer clearing is best effort; input, output and JSON copies, GC and real RSS are not guaranteed. Upload and data retrieval themselves do not contact QQ, invoke v11, read/write a file, make an outbound network request or send a message. The separate restricted image-send path above can use an eligible upload handle.

Before upload effects, the full UTF-8 upload success envelope, including its `file_id` and `echo`, must fit 1 MiB minus 14 bytes. A later data retrieval separately checks its own complete success envelope, including `name`, `data`, `sha256` and its current `echo`. This is a conservative single-frame budget for the default transport with an empty queue, not a delivery guarantee: smaller custom limits, pre-existing WebSocket output or a closed connection can still fail. A failed or lost response can leave the upload outcome unknown; do not automatically retry. See the [listener contract](../../ONEBOT_V12.md#local-data-uploads) for account and lifecycle details.

For an accepted incoming image the runtime seals the exact observed URL as `jiyu-image:v1:` plus a canonical base64url AES-256-GCM payload. This is a local transient handle, **not** QQ encryption or a QQ signature. The URL must pass the same syntax checks and be at most 3,000 UTF-8 bytes; the complete handle is limited to 4,096 characters. The runtime uses an account-bound random key and unique per-key nonces, with at most 2²⁴ issuances per key. Successful `get_file` of one of these handles on that same active runtime returns `{name:'',url:<original string>}` without invoking the v11 action, refreshing the URL or contacting its host. A missing key, altered, revoked or foreign handle returns 20001 and never falls back to the v11 alias path; a detected crypto-provider setup/update failure returns fixed 20002. An exception during authentication finalization cannot be distinguished from an invalid tag and returns 20001. This reserves the prefix: a pre-existing v11 alias beginning with it no longer works through v12 `get_file`, though v11 itself is unchanged. Same-runtime listener reopen and online-status changes retain the key; runtime quiesce/force-close revoke it and a replacement runtime or restart has a different key. Buffer clearing is best effort, not a guarantee about JavaScript or native crypto copies.

Accepted voice records similarly use `jiyu-voice:v1:` plus a canonical base64url AES-256-GCM payload. The voice purpose, randomly generated key, AAD and nonce state are independent of the image issuer. The observed URL must pass the same best-effort syntax checks and be at most 3,000 UTF-8 bytes; the complete ID is at most 4,096 UTF-16 code units, and each voice key permits at most 2²⁴ issuances. Redemption on the same active runtime returns exactly `{name:'',url:<original observed string>}` without a v11 action, URL refresh, download or verification of the file. No QQ source, file identity or file-byte authenticity is established. Same-runtime listener close/reopen retains the key; quiesce, force-close, replacement or restart invalidate its handles. Clearing key buffers is best effort. The voice prefix is reserved even for malformed or revoked IDs and never falls back to v11: a pre-existing v11 alias with that prefix is affected through v12 `get_file`, while v11 alias lookup itself remains unchanged.

Both handle types are transferable bearer references that leak URL length and can be redeemed by a caller permitted to use the issuing runtime's `get_file`. They bind only the URL observed at conversion, not upstream QQ identity, a durable file identity or file bytes. The URL may expire, redirect, need headers, return different content, or be unreachable; v11 events and debug/observer paths may already expose it, and their existing URL resolvers can perform network work. Issuing or redeeming a handle does not itself make a request; upstream conversion is a separate step and may access the network. Production HTTP polling applies separate queue and response budgets to the enlarged event and can drop an oversized event; the distinct ordered-owner prototype can record an internal gap. Neither path demonstrates live QQ interoperability.

`get_user_info` follows the [user action definition](https://12.onebot.dev/interface/user/actions/#get_user_info), with one locally restricted `user_id` parameter: a canonical positive decimal string in `1..4294967295`. Numbers, zero, signs, leading zeroes, whitespace and larger values are invalid. After the existing request snapshot and `self`/`echo` preflight, extra parameters return 10004 before ID validation; missing or invalid IDs return 10003. A valid request calls account-local v11 `get_stranger_info` exactly once with `{user_id: number}`, with no automatic retry. This uint32 ceiling prevents truncation in the current local wire path: `OidbUserInfoRequest.uin` is `uint_32` and Proton encodes it with `>>> 0`. The guard applies only to this v12 action; direct v11 `get_stranger_info` retains its existing input behavior, including possible truncation above uint32. It is not a global QQ ID limit or a OneBot standard limit.

After `await`, the dispatcher checks for Proxy envelopes and data before reflection, rejects arrays, and reads only own data descriptors for `status`, `retcode`, successful `data`, numeric positive safe-integer `user_id` matching the request, and primitive string `nickname` and `remark`. Each string must fit the local 1,024 UTF-16-unit limit. Empty values are preserved; unknown fields are neither enumerated nor accessed. The result is exactly `{user_id: String(id), user_name: nickname, user_displayname: '', user_remark: remark}`. An empty `user_displayname` reflects the absence of an independent source, not proof the user left it unset. The local string limit is distinct from the transport's default 1 MiB output limit; JSON encoding, field names and echo count toward that budget, so an oversized core result may become a transport error or close the connection. Thenable assimilation during `await` can execute a `then` getter before inspection. Malformed results and valid v11 failures 1400/1404 map to fixed 20001 (`invalid user info result`); other valid positive v11 failures and exceptions map to fixed 20002 (`user info unavailable`). Messages omit upstream data and exception details; transport failure-message rewriting may apply.

If v11 context lacks `getStrangerInfo`, or that provider returns null, v11 synthesizes success with the requested ID and empty nickname and remark. After profile fetch failure the provider may fall back to cached profile or friend data; three dataline pseudo-contacts bypass the network lookup. Otherwise the profile fetch may access the network, and optional enterprise profile fetching is best effort. Missing data or success does not establish user existence or friendship. A profile response without `uin` is filled with `requestedUin`; a present inconsistent `uin` is checked. Matching the projected ID therefore does not prove server-side identity. Real QQ behavior is unverified. The shared v11 handler's targeted `get_stranger_info` input, terminal response and exception diagnostics are redacted, and the contact user-profile warning omits sensitive details. This is not global log sanitization: observers receive raw v11 responses, and WebUI SSE, other services and logs may independently disclose data. V11 responses and observer semantics are unchanged.

`get_friend_list` calls the account-local v11 `get_friend_list` exactly once with `{}` and accepts no parameters. After the common preflight, a nonempty parameter object returns 10004 without a handler call. For a successful result, only a non-Proxy dense array of at most 10,000 entries is accepted. Each entry must be a non-Proxy, non-array object with own data properties: positive safe-integer number `user_id`, primitive string `nickname`, and primitive string `remark`. Each string is limited to 1,024 UTF-16 code units and their combined total across all rows to 262,144 UTF-16 code units. Any invalid or over-budget entry rejects the whole result with 20001; no rows are filtered, sorted or deduplicated. In order, entries become `{user_id: String(user_id), user_name: nickname, user_displayname: '', user_remark: remark}`; empty strings and duplicate entries remain. The empty display name reflects the lack of an independent source, not evidence that a user left it unset. These are local validation limits, not network response byte limits; the transport defaults to a separate 1 MiB output limit. JSON encoding, field names and echo also consume that budget. A successful core result may be replaced by transport error 20001, or the connection closed if the fallback with echo also exceeds the limit.

The v11 action returns `[]` when its provider is absent. Thus this result is the v11 roster representation, not proof of real friendships or a complete live list. Like `get_self_info`, upstream data can include fallbacks. This is a read-only outcome, but the v11 implementation may load or cache data or trigger network activity.

JavaScript's thenable assimilation during the single `await` can itself execute a `then` getter before inspection. `get_group_info` follows the [group action definition](https://12.onebot.dev/interface/group/actions/#get_group_info) with local restrictions stricter than the standard's string ID. The v11 action defaults `no_cache` to false; a missing provider or a null provider result produces synthetic success with the original requested ID and an empty name. In the non-member detail path, the upstream implementation assigns the requested ID to the returned object without checking the response's `groupInfo.uin` or `results.uin`. ID equality here validates only the v11 projection, not that the upstream response belongs to the requested group. A missing upstream detail name also becomes an empty string; its real-world frequency is unknown. Real QQ behavior is unverified. `get_group_list` follows the [group action definition](https://12.onebot.dev/interface/group/actions/#get_group_list): no parameters, including no `no_cache`, and exactly one account-local v11 `get_group_list` call with `{}`. Ordinary preflight applies first, including self and echo checks: non-JSON parameters return 10001, while a nonempty valid parameter object returns 10004 without a handler call. Each name is limited to 1,024 UTF-16 units and their total to 262,144 units. The entire result is rejected on invalid or over-limit data; no entries are filtered, sorted or deduplicated. Each projects to `{group_id: String(group_id), group_name}`, preserving order, duplicates and empty names while ignoring v11 extras.

After awaiting the handler, the dispatcher checks for proxies before inspecting the envelope, array or rows, and uses only the required own data descriptors without executing accessors or enumerating extra fields. The account runtime uses the dispatcher's internal HTTP preflight to classify `get_latest_events` on the existing HTTP endpoint. It shares the ordinary request snapshot and top-level checks, but `handle` and WebSocket action requests still return 10002 for this action; `get_supported_actions` does not advertise it. The internal HTTP context is not a same-process security boundary. Poll parameters default to zero and accept nonnegative JavaScript safe integers; unsupported parameters return 10004, invalid values return 10003, and `timeout` is capped at 10 seconds (also 10003 above the cap). A poll echo longer than 4,096 UTF-16 code units returns 10001 after earlier preflight checks if the response remains writable. The snapshot rejects non-finite numbers earlier with 10001. These limits are narrower than the standard's int64 range. HTTP JSON has already been parsed before this seam, so duplicate JSON keys cannot be detected here. See [current polling behavior and limits](../../V12_HTTP_POLL_DESIGN.md#current-http-polling-behavior).

Ordinary preflight tokens are bound to one dispatcher instance and consumed at most once. A holder may retain an unused token indefinitely; the WeakMap offers no explicit discard or revoke operation and establishes no generation, authorization, cancellation or deadline guarantees. Before executing a prepared ordinary action, a future trusted transport must validate its generation, authorization, cancellation and deadline, and control token references and their number. Deterministic revocation requires a separate future design. The outer classification object is frozen, but `error.response` is not recursively frozen; these objects do not protect against tampering by same-process code.

The constructor snapshots the value of `options.self` before validating and retaining it. Within that value and its subtree, accessors and proxies are rejected without executing their getters or traps; evaluating the `options.self` or `options.version` properties can itself invoke an options-object getter. The current runtime supplies a plain self object. JSON-shaped extensions are copied in the snapshot and deeply frozen to protect account state; rejecting self accessors and proxies is a change for those edge cases. As `get_status` shallow-copies self, nested extension values in its response remain frozen too; this observably narrows behavior for nonstandard self extensions.

## Integration contract

`V12Dispatcher` takes `{ self, version: {impl, version}, api, getStatus, getSentMessageTime }` and `handle(unknown)` returns `Promise<V12Response>`. `api` is structurally compatible with the real per-account `ApiHandler.handle`. `getStatus` must reflect actual account state. `getSentMessageTime(id)` resolves the same account's recorded send-time estimate in Unix seconds, for example `(await messageStore.findMeta(id))?.timestamp ?? null`. `findMeta` is asynchronous and may return null; `finalizeSend` persists the receipt timestamp before returning. The Bridge uses the upstream `timestamp1` when present and otherwise a local clock fallback, while the store does not record which source was used. This timestamp is a Jiyu send-time estimate, not necessarily a QQ-confirmed time. Never generate an additional value when stored metadata is missing. For send and delete, v11 1400 maps to 10003, 1404 to 20001, and other ambiguous handler/execution errors to 20002; inconsistent status and retcode map to 20001. This does not guess a platform error from a generic v11 failure. The actual send may have completed even when action execution or subsequent timestamp lookup fails; errors explicitly say not to retry automatically. The integration must record the effect/uncertainty without logging private values and must not replay such actions.

`convertV11Event(event, self)` consumes events created by the internal v11 converter, not arbitrary plugin objects, and performs account checking before conversion. The runtime must isolate and log conversion failures without interrupting v11 event dispatch. `createConnectEvent(version)`, `createStatusUpdateEvent(self, status)` and `createHeartbeatEvent(intervalMs)` provide isolated meta frames. Connect must be the first event after WS establishment; the transport provides accurate version, status, auth, lifecycle/drain and event policies. The account runtime optionally schedules heartbeat frames independently of QQ and v11 events, as described in [the listener configuration](../../ONEBOT_V12.md#configuration); the builder alone does not schedule them. The v12 standards require Authorization header precedence over the query token: the existing v11 auth helper has different semantics and must not be reused unchanged for a v12 listener.
