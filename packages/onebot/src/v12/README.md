# OneBot 12 core (partial, transport-independent)

This directory implements a per-account protocol translation core, not a OneBot server or a claim of full OneBot 12 conformance. The owning account lifecycle must instantiate it explicitly; no existing v11 behavior or network endpoint is changed by these modules. Reference: [action request](https://12.onebot.dev/connect/data-protocol/action-request/), [action response and codes](https://12.onebot.dev/connect/data-protocol/action-response/), [meta actions](https://12.onebot.dev/interface/meta/actions/), [meta events](https://12.onebot.dev/interface/meta/events/), [message actions](https://12.onebot.dev/interface/message/actions/), [message segments](https://12.onebot.dev/interface/message/segments/), [events](https://12.onebot.dev/connect/data-protocol/event/). OneBot 12 is a candidate standard.

## Support matrix

| Capability                                                                                     | Current core                                                                                         |
| ---------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------- |
| `get_version`, `get_status`, `get_supported_actions`                                           | Account-scoped; version and live status injected by owner                                            |
| `get_self_info`                                                                                | No parameters; validated account-local v11 login ID and nickname, with an empty `user_displayname`   |
| `send_message`                                                                                 | Private and group; text only, accepted as string, one text segment, or an array of text segments     |
| `delete_message`                                                                               | Existing account-local v11 nonzero signed 32-bit message IDs                                         |
| Message events                                                                                 | Incoming v11 friend/private and normal/group text and `at` segments; no fabricated media IDs        |
| Group notices                                                                                  | Valid v11 `group_recall` and `group_decrease/leave` map to v12 notices                              |
| Meta event builders                                                                            | `connect`, `heartbeat`, `status_update`; transport controls emission and ordering                    |
| Other actions                                                                                  | 10002; not passed through to v11                                                                     |
| Other segments/parameters                                                                      | Explicit unsupported result/error; never silently dropped                                            |
| `get_latest_events`, other notices, requests, self-sent events, temporary chats, media and file APIs | Not implemented                                                                                      |
| HTTP, WebSocket, Webhook, auth, event buffering                                                | Not implemented here; transport owner must implement and test separately                             |

Jiyu echoes every supplied string `echo` unchanged, including the empty string, on success and failure. The candidate standard explicitly recommends echoing non-empty strings; Jiyu's empty-string echo is an additional compatibility behavior. In-process `handle(unknown)` rejects Proxy objects before reflection and snapshots JSON-shaped input through own data-property descriptors without evaluating getters. It rejects accessors, cycles, non-finite numbers and non-plain objects, and applies a maximum of 8192 nodes, 32 nested levels, 4096 array items or object properties and 1,048,576 UTF-16 units per string. Errors return sanitized 10001; a safely observed own data-property string `echo` is retained except when the request itself is a Proxy, whose properties are never examined.

Supported event conversion requires an unmodified v11 array-format `message` and `raw_message`. It maps a v11 `at` with a canonical positive account ID to `mention`, and `at` with `qq: 'all'` to `mention_all`; `alt_message` renders them as `@<user_id>` and `@全体成员`, respectively, without inserting spaces or interpreting CQ-escaped `raw_message` as plain text. This maps the v11 representation, not independently verified QQ semantics: the upstream rich-body decoder can turn an unresolved mention UIN into zero, which the v11 converter represents as `all`. Other event types and v11 message semantics require a separately reviewed mapping. A valid v11 `group_recall` is converted to `notice.group_message_delete`, with `recall` when the author and operator match and an empty subtype otherwise. Its message ID preserves the v11 value; the upstream resolver may hash a missing sequence, so it does not prove a QQ history match. Unresolved or zero author/operator IDs are rejected. A valid v11 `group_decrease` with subtype `leave` maps to `notice.group_member_decrease`, always with an empty subtype: an absent upstream reason can default to `leave`, and the source event or actor can be locally synthesized. The v12 mapping preserves the v11 fields rather than proving QQ-side origin or time. Unresolved or zero member/operator/group IDs are rejected; other decrease subtypes remain unsupported. Other known non-message v11 events return null. Unsupported/malformed mapped events throw, not a partial message. Event IDs are generated independently and are not message IDs. IDs in v12 are strings, but the current QQ/v11 service can route only canonical positive decimal safe-integer account/target IDs and canonical nonzero signed-int32 message IDs. Prefix zeroes, scientific notation and unsafe values are not normalized or rounded. The configured v12 `self` is compared exactly by platform and user_id; malformed or mismatched supplied self never reaches actions. A shared multi-account transport requires separate routing and authorization and must not treat this per-account dispatcher as a global registry.

`get_self_info` calls the account-local v11 `get_login_info` once with `{}`. Its numeric safe positive ID must match the configured self ID exactly; `user_name` is the returned nickname, even when empty, and `user_displayname` is `''` because no independent display name is available. The actual v11 login-info source may already substitute the UIN when its nickname is missing. Malformed or inconsistent results and v11 failures 1400/1404 return fixed 20001; other well-formed v11 failures and thrown errors return fixed 20002. After the awaited API result is received, the dispatcher rejects Proxy responses and data and inspects required own data properties without executing getters. JavaScript Promise resolution itself can read a returned object's `then` before that inspection; an exception there maps to 20002. These fixed core messages contain no upstream exception or account details.

The existing v12 transport may replace most failure messages with its generic side-effect uncertainty warning, including for this read-only action. It preserves the retcode, subject to its existing response and connection limits. See the [user action definition](https://12.onebot.dev/interface/user/actions/).

The dispatcher has an internal, currently unwired HTTP preflight seam for future integration. It shares the ordinary request snapshot and top-level checks; it does not register an action or endpoint, and `handle` still returns 10002 for `get_latest_events`. Only the transport owner should obtain the internal HTTP context; this is not a same-process security boundary. Poll parameters default to zero and accept nonnegative JavaScript safe integers; unsupported parameters return 10004, invalid values return 10003, and the implementation caps `timeout` at 10 seconds (also 10003 above the cap). The snapshot rejects non-finite numbers earlier with 10001. These limits are narrower than the standard's int64 range. Input JSON has already been parsed before this seam, so duplicate JSON keys cannot be detected here.

Ordinary preflight tokens are bound to one dispatcher instance and consumed at most once. A holder may retain an unused token indefinitely; the WeakMap offers no explicit discard or revoke operation and establishes no generation, authorization, cancellation or deadline guarantees. Before executing a prepared ordinary action, a future trusted transport must validate its generation, authorization, cancellation and deadline, and control token references and their number. Deterministic revocation requires a separate future design. The outer classification object is frozen, but `error.response` is not recursively frozen; these objects do not protect against tampering by same-process code.

The constructor snapshots the value of `options.self` before validating and retaining it. Within that value and its subtree, accessors and proxies are rejected without executing their getters or traps; evaluating the `options.self` or `options.version` properties can itself invoke an options-object getter. The current runtime supplies a plain self object. JSON-shaped extensions are copied in the snapshot and deeply frozen to protect account state; rejecting self accessors and proxies is a change for those edge cases. As `get_status` shallow-copies self, nested extension values in its response remain frozen too; this observably narrows behavior for nonstandard self extensions.

## Integration contract

`V12Dispatcher` takes `{ self, version: {impl, version}, api, getStatus, getSentMessageTime }` and `handle(unknown)` returns `Promise<V12Response>`. `api` is structurally compatible with the real per-account `ApiHandler.handle`. `getStatus` must reflect actual account state. `getSentMessageTime(id)` resolves the same account's recorded send-time estimate in Unix seconds, for example `(await messageStore.findMeta(id))?.timestamp ?? null`. `findMeta` is asynchronous and may return null; `finalizeSend` persists the receipt timestamp before returning. The Bridge uses the upstream `timestamp1` when present and otherwise a local clock fallback, while the store does not record which source was used. This timestamp is a Jiyu send-time estimate, not necessarily a QQ-confirmed time. Never generate an additional value when stored metadata is missing. For send and delete, v11 1400 maps to 10003, 1404 to 20001, and other ambiguous handler/execution errors to 20002; inconsistent status and retcode map to 20001. This does not guess a platform error from a generic v11 failure. The actual send may have completed even when action execution or subsequent timestamp lookup fails; errors explicitly say not to retry automatically. The integration must record the effect/uncertainty without logging private values and must not replay such actions.

`convertV11Event(event, self)` consumes events created by the internal v11 converter, not arbitrary plugin objects, and performs account checking before conversion. The runtime must isolate and log conversion failures without interrupting v11 event dispatch. `createConnectEvent(version)`, `createStatusUpdateEvent(self, status)` and `createHeartbeatEvent(intervalMs)` provide isolated meta frames. Connect must be the first event after WS establishment; the transport provides accurate version, status, auth, lifecycle/drain and event policies. The v12 standards require Authorization header precedence over the query token: the existing v11 auth helper has different semantics and must not be reused unchanged for a v12 listener.
